Name
####

org.freedesktop.hostname1 — The D-Bus interface of systemd-hostnamed

Introduction
############

:ref:`systemd-hostnamed.service(8)` is a system service that can be used to control the hostname and related machine metadata from user programs. This page describes the hostname semantics and the D-Bus interface.

The D-Bus API
#############

Whenever the hostname or other metadata is changed via the daemon, :code:`PropertyChanged` signals are sent out to subscribed clients. Changing a hostname using this interface is authenticated via `polkit <https://www.freedesktop.org/software/polkit/docs/latest/>`_.

Semantics
#########

The :code:`StaticHostname` property exposes the "static" hostname configured in :code:`/etc/hostname`. It is not always in sync with the current hostname as returned by the :man-pages:`gethostname(3)` system call. If no static hostname is configured this property will be the empty string.

When :ref:`systemd(1)` or :ref:`systemd-hostnamed.service(8)` set the hostname, this static hostname *has the highest priority*\..

The :code:`Hostname` property exposes the actual hostname configured in the kernel via :man-pages:`sethostname(2)`. It can be different from the static hostname. This property is never empty.

The :code:`PrettyHostname` property exposes the *pretty hostname* which is a free-form UTF-8 hostname for presentation to the user. User interfaces should ensure that the pretty hostname and the static hostname stay in sync. E.g. when the former is which is a free-form UTF-8 hostname for presentation to the user. User interfaces should ensure that the pretty hostname and the static hostname stay in sync. E.g. when the former is "Lennart’s Computer" the latter should be "lennarts-computer". If no pretty hostname is set this setting will be the empty string. Applications should then find a suitable fallback, such as the dynamic hostname.

The :code:`DefaultHostname` property exposes the default hostname (configured through :man-pages:`os-release(5)`, or a fallback set at compilation time).

The :code:`HostnameSource` property exposes the origin of the currently configured hostname. One of "static" (set from :code:`/etc/hostname`), "transient" (a non-permanent hostname from an external source), "default" (the value from :code:`os-release` or the compiled-in fallback).

The :code:`IconName` property exposes the *icon name* following the XDG icon naming spec. If not set, information such as the chassis type (see below) is used to find a suitable fallback icon name (i.e. following the XDG icon naming spec. If not set, information such as the chassis type (see below) is used to find a suitable fallback icon name (i.e. "computer-laptop" vs. "computer-desktop" is picked based on the chassis information). If no such data is available, the empty string is returned. In that case an application should fall back to a replacement icon, for example "computer". If this property is set to the empty string, the automatic fallback name selection is enabled again.

The :code:`Chassis` property exposes a *chassis type*\, one of the currently defined chassis types: , one of the currently defined chassis types: "desktop", "laptop", "server", "tablet", "handset", as well as the special chassis types "vm" and "container" for virtualized systems. Note that in most cases the chassis type will be determined automatically from DMI/SMBIOS/ACPI firmware information. Writing to this setting is hence useful only to override misdetected chassis types, or to configure the chassis type if it could not be auto-detected. Set this property to the empty string to reenable the automatic detection of the chassis type from firmware information.

Note that :code:`systemd-hostnamed` starts only on request and terminates after a short idle period. This effectively means that :code:`PropertyChanged` messages are not sent out for changes made directly on the files (as in: administrator edits the files with vi). This is the intended behavior: manual configuration changes should require manual reloading.

The transient (dynamic) hostname exposed by the :code:`Hostname` property maps directly to the kernel hostname. This hostname should be assumed to be highly dynamic, and hence should be watched directly, without depending on :code:`PropertyChanged` messages from :code:`systemd-hostnamed`. To accomplish this, open :code:`/proc/sys/kernel/hostname` and :man-pages:`poll(3)` for :code:`SIGHUP` which is triggered by the kernel every time the hostname changes. Again: this is special for the transient (dynamic) hostname, and does not apply to the configured (fixed) hostname.

Applications may read the hostname data directly if hostname change notifications are not necessary. Use :man-pages:`gethostname(2)`, :code:`/etc/hostname` (possibly with per-distribution fallbacks), and :man-pages:`machine-info(5)` for that. For more information on these files and syscalls see the respective man pages.

:code:`KernelName`, :code:`KernelRelease`, and :code:`KernelVersion` expose the kernel name (e.g. "Linux"), release (e.g. "5.0.0-11"), and version (i.e. the build number, e.g. "#11") as reported by :man-pages:`uname(2)`. :code:`OperatingSystemPrettyName`, :code:`OperatingSystemCPEName`, and :code:`HomeURL` expose the :code:`PRETTY_NAME=`, :code:`CPE_NAME=` and :code:`HOME_URL=` fields from :man-pages:`os-release(5)`. The purpose of those properties is to allow remote clients to access this information over D-Bus. Local clients can access the information directly.

:code:`MachineID` expose the 128bit machine ID, see :man-pages:`machine-id(5)` for details.

:code:`BootID` expose the 128bit boot ID, as per :code:`/proc/sys/kernel/random/boot_id`.

:code:`VSockCID` exposes the system's local :code:`AF_VSOCK` CID (Context Identifier, i.e. address) for the system, if one is available in the virtual machine environment. Set to :code:`UINT32_MAX` otherwise. See :man-pages:`vsock(7)` for details.

:code:`OperatingSystemSupportEnd` exposes when the OS' vendor support ends, if this information is known. It's an unsigned 64bit value, in µs since the UNIX epoch, UTC. If this information is not known carries the value 2^64-1, i.e. :code:`UINT64_MAX`.

:code:`OperatingSystemImageID` and :code:`OperatingSystemImageVersion` expose the OS image name and version if available, or contain empty strings otherwise. This mostly corresponds to the :code:`IMAGE_ID=` and :code:`IMAGE_VERSION=` fields of the :code:`os-release` file.

:code:`HardwareVendor`, :code:`HardwareModel`, :code:`HardwareSKU`, and :code:`HardwareVersion` expose vendor information about the hardware of the system. The stock keeping unit (SKU) describes a distinct type of hardware for sale, purchase or inventory management. The SKU and version are only available if they deviate from the model and among each other. Thereby the version is more specific and only available if it differs from the model and SKU. If no such information can be determined these properties are set to empty strings.

:code:`FirmwareVersion` and :code:`FirmwareVendor` expose information about the system's firmware, i.e. a version string and a vendor name. If no such information can be determined these properties are set to empty strings.

:code:`FirmwareDate` exposes the firmware build date, if that information is known. It's an unsigned 64bit value, in µs since the UNIX epoch, UTC. If not known :code:`UNIT64_MAX`.

:code:`ChassisAssetTag` exposes an unique identifier of the system chassis. If this information is not known this property is set to an empty string.

Methods
#######

:code:`SetHostname()` sets the transient (dynamic) hostname, which is used if no static hostname is set. This value must be an internet-style hostname, 7-bit lowercase ASCII, no special chars/spaces. An empty string will unset the transient hostname.

:code:`SetStaticHostname()` sets the static hostname which is exposed by the :code:`StaticHostname` property. When called with an empty argument, the static configuration in :code:`/etc/hostname` is removed. Since the static hostname has the highest priority, calling this function usually affects also the :code:`Hostname` property and the effective hostname configured in the kernel.

:code:`SetPrettyHostname()` sets the pretty hostname which is exposed by the :code:`PrettyHostname` property.

:code:`SetIconName()`, :code:`SetChassis()`, :code:`SetDeployment()`, and :code:`SetLocation()` set the properties :code:`IconName` (the name of the icon representing for the machine), :code:`Chassis` (the machine form factor), :code:`Deployment` (the system deployment environment), and :code:`Location` (physical system location), respectively.

:code:`PrettyHostname`, :code:`IconName`, :code:`Chassis`, :code:`Deployment`, and :code:`Location` are stored in :code:`/etc/machine-info`. See :man-pages:`machine-info(5)` for the semantics of those settings.

:code:`GetProductUUID()` returns the "product UUID" as exposed by the kernel based on DMI information in :code:`/sys/class/dmi/id/product_uuid`. Reading the file directly requires root privileges, and this method allows access to unprivileged clients through the polkit framework.

:code:`GetHardwareSerial()` returns the "hardware serial" as exposed by the kernel based on DMI information. Reading the file directly requires root privileges, and this method allows access to unprivileged clients through the polkit framework.

:code:`Describe()` returns a JSON representation of all properties in one.

Security
########

The :code:`interactive` boolean parameters can be used to control whether polkit should interactively ask the user for authentication credentials if required.

The polkit action for :code:`SetHostname()` is :code:`org.freedesktop.hostname1.set-hostname`. For :code:`SetStaticHostname()` and :code:`SetPrettyHostname()` it is :code:`org.freedesktop.hostname1.set-static-hostname`. For :code:`SetIconName()`, :code:`SetChassis()`, :code:`SetDeployment()` and :code:`SetLocation()` it is :code:`org.freedesktop.hostname1.set-machine-info`.

Recommendations
###############

Here are three examples that show how the pretty hostname and the icon name should be used: *    When registering DNS-SD services: use the pretty hostname in the service name, and pass the icon name in the TXT data, if there is an icon name. Browsing clients can then show the server icon on each service. This is especially useful for WebDAV applications or UPnP media sharing.

*    Set the bluetooth name to the pretty hostname.

*    When your file browser has a "Computer" icon, replace the name with the pretty hostname if set, and the icon with the icon name, if it is set.

To properly handle name lookups with changing local hostnames without having to edit :code:`/etc/hosts`, we recommend using :code:`systemd-hostnamed` in combination with :man-pages:`nss-myhostname(8)`.

Here are some recommendations to follow when generating a static (internet) hostname from a pretty name: *    Generate a single DNS label only, not an FQDN. That means no dots allowed. Strip them, or replace them with "-".

*    It's probably safer to not use any non-ASCII chars, even if DNS allows this in some way these days. In fact, restrict your charset to "a-zA-Z0-9" and "-". Strip other chars, or try to replace them in some smart way with chars from this set, for example "ä" → "ae", and use "-" as the replacement for all punctuation characters and whitespace.

*    Try to avoid creating repeated "-", as well as "-" as the first or last char.

*    Limit the hostname to 63 chars, which is the length of a DNS label.

*    If after stripping special chars the empty string is the result, you can pass this as-is to :code:`systemd-hostnamed` in which case it will automatically use a suitable fallback.

*    Uppercase characters should be replaced with their lowercase equivalents.

Note that while :code:`systemd-hostnamed` applies some checks to the hostname you pass they are much looser than the recommendations above. For example, :code:`systemd-hostnamed` will also accept "_" in the hostname, but we recommend not using this to avoid clashes with DNS-SD service types. Also :code:`systemd-hostnamed` allows longer hostnames, but because of the DNS label limitations, we recommend not making use of this.

Here are a couple of example conversions: *    "Lennart's PC" → "lennarts-pc"

*    "Müllers Computer" → "muellers-computer"

*    "Voran!" → "voran"

*    "Es war einmal ein Männlein" → "es-war-einmal-ein-maennlein"

*    "Jawoll. Ist doch wahr!" → "jawoll-ist-doch-wahr"

*    "レナート" → "localhost"

*    "...zack!!! zack!..." → "zack-zack"

Of course, an already valid internet hostname label you enter and pass through this conversion should stay unmodified, so that users have direct control of it, if they want — by simply ignoring the fact that the pretty hostname is pretty and just edit it as if it was the normal internet name.
