===============================
systemd-cryptsetup-generator(8)
===============================

Name
####

systemd-cryptsetup-generator — Unit generator for

Synopsis
########

:code:`/usr/lib/systemd/system-generators/systemd-cryptsetup-generator`

Description
###########

:code:`systemd-cryptsetup-generator` is a generator that translates :code:`/etc/crypttab` into native systemd units early at boot and when configuration of the system manager is reloaded. This will create :ref:`systemd-cryptsetup@.service(8)` units as necessary.

:code:`systemd-cryptsetup-generator` implements :ref:`systemd.generator(7)`.

Kernel Command Line
###################

:code:`systemd-cryptsetup-generator` understands the following kernel command line parameters:

.. systemd:option:: luks=, rd.luks=
   :group: kernel-commandline-options

   Takes a boolean argument. Defaults to "yes". If "no", disables the generator entirely. :systemd:var:`rd.luks=` is honored only in the initrd while :systemd:var:`luks=` is honored by both the main system and in the initrd.

   .. versionadded:: 186

.. systemd:option:: luks.crypttab=, rd.luks.crypttab=
   :group: kernel-commandline-options

   Takes a boolean argument. Defaults to "yes". If "no", causes the generator to ignore any devices configured in :code:`/etc/crypttab` (:systemd:var:`luks.uuid=` will still work however). :systemd:var:`rd.luks.crypttab=` is honored only in initrd while :systemd:var:`luks.crypttab=` is honored by both the main system and in the initrd.

   .. versionadded:: 186

.. systemd:option:: luks.uuid=, rd.luks.uuid=
   :group: kernel-commandline-options

   Takes a LUKS superblock UUID as argument. This will activate the specified device as part of the boot process as if it was listed in :code:`/etc/crypttab`. This option may be specified more than once in order to set up multiple devices. :systemd:var:`rd.luks.uuid=` is honored only in the initrd, while :systemd:var:`luks.uuid=` is honored by both the main system and in the initrd.

   If :code:`/etc/crypttab` contains entries with the same UUID, then the name, keyfile and options specified there will be used. Otherwise, the device will have the name "luks-UUID".

   If :code:`/etc/crypttab` exists, only those UUIDs specified on the kernel command line will be activated in the initrd or the real root.

   .. versionadded:: 186

.. systemd:option:: luks.name=, rd.luks.name=
   :group: kernel-commandline-options

   Takes a LUKS super block UUID followed by an "=" and a name. This implies :systemd:var:`rd.luks.uuid=` or :systemd:var:`luks.uuid=` and will additionally make the LUKS device given by the UUID appear under the provided name.

   This parameter is the analogue of the first :man-pages:`crypttab(5)` field :emphasis:`volume-name`.

   :systemd:var:`rd.luks.name=` is honored only in the initrd, while :systemd:var:`luks.name=` is honored by both the main system and in the initrd.

   .. versionadded:: 218

.. systemd:option:: luks.data=, rd.luks.data=
   :group: kernel-commandline-options

   Takes a LUKS super block UUID followed by a "=" and a block device specification for device hosting encrypted data.

   For those entries specified with :systemd:var:`rd.luks.uuid=` or :systemd:var:`luks.uuid=`, the data device will be set to the one specified by :systemd:var:`rd.luks.data=` or :systemd:var:`luks.data=` of the corresponding UUID.

   LUKS data device parameter is useful for specifying encrypted data devices with detached headers specified in :systemd:var:`luks.options` entry containing "header=" argument. For example, :systemd:var:`rd.luks.uuid=`\b40f1abf-2a53-400a-889a-2eccc27eaa40 :systemd:var:`rd.luks.options=`\b40f1abf-2a53-400a-889a-2eccc27eaa40=header=/path/to/luks.hdr :systemd:var:`rd.luks.data=`\b40f1abf-2a53-400a-889a-2eccc27eaa40=/dev/sdx. Hence, in this case, we will attempt to unlock LUKS device assembled from data device "/dev/sdx" and LUKS header (metadata) put in "/path/to/luks.hdr" file. This syntax is for now only supported on a per-device basis, i.e. you have to specify LUKS device UUID.

   This parameter is the analogue of the second :man-pages:`crypttab(5)` field :emphasis:`encrypted-device`.

   :systemd:var:`rd.luks.data=` is honored only in the initrd, while :systemd:var:`luks.data=` is honored by both the main system and in the initrd.

   .. versionadded:: 247

.. systemd:option:: luks.key=, rd.luks.key=
   :group: kernel-commandline-options

   Takes a password file name as argument or a LUKS super block UUID followed by a "=" and a password file name.

   For those entries specified with :systemd:var:`rd.luks.uuid=` or :systemd:var:`luks.uuid=`, the password file will be set to the one specified by :systemd:var:`rd.luks.key=` or :systemd:var:`luks.key=` of the corresponding UUID, or the password file that was specified without a UUID.

   It is also possible to specify an external device which should be mounted before we attempt to unlock the LUKS device. systemd-cryptsetup will use password file stored on that device. Device containing password file is specified by appending colon and a device identifier to the password file path. For example, :systemd:var:`rd.luks.uuid=`\b40f1abf-2a53-400a-889a-2eccc27eaa40 :systemd:var:`rd.luks.key=`\b40f1abf-2a53-400a-889a-2eccc27eaa40=/keyfile:LABEL=keydev. Hence, in this case, we will attempt to mount file system residing on the block device with label "keydev". This syntax is for now only supported on a per-device basis, i.e. you have to specify LUKS device UUID.

   This parameter is the analogue of the third :man-pages:`crypttab(5)` field :emphasis:`key-file`.

   :systemd:var:`rd.luks.key=` is honored only in the initrd, while :systemd:var:`luks.key=` is honored by both the main system and in the initrd.

   .. versionadded:: 202

.. systemd:option:: luks.options=, rd.luks.options=
   :group: kernel-commandline-options

   Takes a LUKS super block UUID followed by an "=" and a string of options separated by commas as argument. This will override the options for the given UUID.

   If only a list of options, without a UUID, is specified, they apply to any UUIDs not specified elsewhere, and without an entry in :code:`/etc/crypttab`.

   This parameter is the analogue of the fourth :man-pages:`crypttab(5)` field :emphasis:`options`.

   It is possible to specify an external device which should be mounted before we attempt to unlock the LUKS device. systemd-cryptsetup will assemble LUKS device by combining data device specified in :systemd:var:`luks.data` with detached LUKS header found in "header=" argument. For example, :systemd:var:`rd.luks.uuid=`\b40f1abf-2a53-400a-889a-2eccc27eaa40 :systemd:var:`rd.luks.options=`\b40f1abf-2a53-400a-889a-2eccc27eaa40=header=/luks.hdr:LABEL=hdrdev :systemd:var:`rd.luks.data=`\b40f1abf-2a53-400a-889a-2eccc27eaa40=/dev/sdx. Hence, in this case, we will attempt to mount file system residing on the block device with label "hdrdev", and look for "luks.hdr" on that file system. Said header will be used to unlock (decrypt) encrypted data stored on /dev/sdx. This syntax is for now only supported on a per-device basis, i.e. you have to specify LUKS device UUID.

   :systemd:var:`rd.luks.options=` is honored only by initial RAM disk (initrd) while :systemd:var:`luks.options=` is honored by both the main system and in the initrd.

   .. versionadded:: 208
