==============
pam_systemd(8)
==============

Name
####

pam_systemd — Register user sessions in the systemd login manager

Synopsis
########

:code:`pam_systemd.so`

Description
###########

:code:`pam_systemd` registers user sessions with the systemd login manager :ref:`systemd-logind.service(8)`, and hence the systemd control group hierarchy.

The module also applies various resource management and runtime parameters to the new session, as configured in the `JSON User Records <https://systemd.io/USER_RECORD>`_ of the user, when one is defined.

On login, this module — in conjunction with :code:`systemd-logind.service` — ensures the following:

1.    If it does not exist yet, the user runtime directory :code:`/run/user/$UID` is either created or mounted as new "tmpfs" file system with quota applied, and its ownership changed to the user that is logging in.

2.    The :code:`$XDG_SESSION_ID` environment variable is initialized. If auditing is available and :code:`pam_loginuid.so` was run before this module (which is highly recommended), the variable is initialized from the auditing session id (:code:`/proc/self/sessionid`). Otherwise, an independent session counter is used.

3.    A new systemd scope unit is created for the session. If this is the first concurrent session of the user, an implicit per-user slice unit below :code:`user.slice` is automatically created and the scope placed into it. An instance of the system service :code:`user@.service`, which runs the systemd user manager instance, is started.

4.    The "$TZ", "$EMAIL" and "$LANG" environment variables are configured for the user, based on the respective data from the user's JSON record (if it is defined). Moreover, any environment variables explicitly configured in the user record are imported, and the umask, nice level, and resource limits initialized.

On logout, this module ensures the following:

1.    If enabled in :man-pages:`logind.conf(5)` (:code:`KillUserProcesses=`), all processes of the session are terminated. If the last concurrent session of a user ends, the user's systemd instance will be terminated too, and so will the user's slice unit.

2.    If the last concurrent session of a user ends, the user runtime directory :code:`/run/user/$UID` and all its contents are removed, too.

If the system was not booted up with systemd as init system, this module does nothing and immediately returns :code:`PAM_SUCCESS`.

Options
#######

The following options are understood:

.. systemd:option:: class=
   :group: pam-directives

   Takes a string argument which sets the session class. The :systemd:var:`XDG_SESSION_CLASS` environment variable (see below) takes precedence. See :ref:`sd_session_get_class(3)` for a way to query the class of a session. The following session classes are defined:

   .. list-table:: Session Classes
      :header-rows: 1

      * - Name
        - Explanation
      * - :systemd:constant:`user`
        - A regular interactive user session. This is the default class for sessions for which a TTY or X display is known at session registration time.
      * - :systemd:constant:`user-early`
        - Similar to :systemd:constant:`user` but sessions of this class are not ordered after :ref:`systemd-user-sessions.service(8)`, i.e. may be started before regular sessions are allowed to be established. This session class is the default for sessions of the root user that would otherwise qualify for the :systemd:constant:`user` class, see above. (Added in v256.)
      * - :systemd:constant:`user-light`
        - Similar to :systemd:constant:`user`, but sessions of this class will not pull in the :man-pages:`user@.service(5)` of the user, and thus possibly have no service manager of the user running. (Added in v258.)
      * - :systemd:constant:`user-early-light`
        - Similar to :systemd:constant:`user-early`, but sessions of this class will not pull in the :man-pages:`user@.service(5)` of the user, and thus possibly have no service manager of the user running. (Added in v258.)
      * - :systemd:constant:`user-incomplete`
        - Similar to :systemd:constant:`user` but for sessions which are not fully set up yet, i.e. have no home directory mounted or similar. This is used by :ref:`systemd-homed.service(8)` to allow users to log in via :man-pages:`ssh(1)` before their home directory is mounted, delaying the mount until the user provided the unlock password. Sessions of this class are upgraded to the regular :systemd:constant:`user` class once the home directory is activated.
      * - :systemd:constant:`greeter`
        - Similar to :systemd:constant:`user` but for sessions that are spawned by a display manager ephemerally and which prompt the user for login credentials.
      * - :systemd:constant:`lock-screen`
        - Similar to :systemd:constant:`user` but for sessions that are spawned by a display manager ephemerally and which show a lock screen that can be used to unlock locked user accounts or sessions.
      * - :systemd:constant:`background`
        - Used for background sessions, such as those invoked by :die-net:`cron(8)` and similar tools. This is the default class for sessions for which no TTY or X display is known at session registration time.
      * - :systemd:constant:`background-light`
        - Similar to :systemd:constant:`background`, but sessions of this class will not pull in the :man-pages:`user@.service(5)` of the user, and thus possibly have no service manager of the user running. (Added in v256.)
      * - :systemd:constant:`manager`
        - The :man-pages:`user@.service(5)` service of the user is registered under this session class. (Added in v256.)
      * - :systemd:constant:`manager-early`
        - Similar to :systemd:constant:`manager`, but for the root user. Compare with the :systemd:constant:`user` vs. :systemd:constant:`user-early` situation. (Added in v256.)
      * - :systemd:constant:`none`
        - Skips registering this session with logind. No session scope will be created, and the user service manager will not be started. (Added in v258.)

   If no session class is specified via either the PAM module option or via the :systemd:var:`$XDG_SESSION_CLASS` environment variable, the class is automatically chosen, depending on various session parameters, such as the session type (if known), whether the session has a TTY or X11 display, and the user disposition. Note that various tools allow setting the session class for newly allocated PAM sessions explicitly by means of the :systemd:var:`$XDG_SESSION_CLASS` environment variable. For example, classic UNIX cronjobs support environment variable assignments (see :man-pages:`crontab(5)`), which may be used to choose between the :systemd:constant:`background` and :systemd:constant:`background-light` session class individually per cronjob, or :code:`run0 --setenv=XDG_SESSION_CLASS=user-light` may be used to choose between :systemd:constant:`user` and :systemd:constant:`user-light` for invoked privileged sessions.

   .. versionadded:: 197

.. systemd:option:: type=
   :group: pam-directives

   Takes a string argument which sets the session type. The :systemd:var:`XDG_SESSION_TYPE` environment variable (see below) takes precedence. One of :systemd:constant:`unspecified`, :systemd:constant:`tty`, :systemd:constant:`x11`, :systemd:constant:`wayland`, :systemd:constant:`mir`, or :systemd:constant:`web`. See :ref:`sd_session_get_type(3)` for details about the session type.

   .. versionadded:: 209

.. systemd:option:: desktop=
   :group: pam-directives

   Takes a single, short identifier string for the desktop environment. The :systemd:var:`XDG_SESSION_DESKTOP` environment variable (see below) takes precedence. This may be used to indicate the session desktop used, where this applies and if this information is available. For example: :systemd:constant:`GNOME`, or :systemd:constant:`KDE`. It is recommended to use the same identifiers and capitalization as for :systemd:var:`$XDG_CURRENT_DESKTOP`, as defined by the `Desktop Entry Specification <https://standards.freedesktop.org/desktop-entry-spec/latest/>`_. (However, note that the option only takes a single item, and not a colon-separated list like :systemd:var:`$XDG_CURRENT_DESKTOP`.) See :ref:`sd_session_get_desktop(3)` for further details.

   .. versionadded:: 240

.. systemd:option:: area=
   :group: pam-directives

   Takes a filename as parameter. If specified and the user logs into their account the :systemd:var:`$HOME` environment variable will be set to :code:`~/Areas/` suffixed by the specified string, but only if that directory exists. Moreover, the :systemd:var:`$XDG_AREA` variable will be set to the (unprefixed) parameter.

   This functionality may be used to maintain multiple separate secondary home directories within the primary home directory of the user. Typically, the area to log into is specified while logging in, if the account permits that (accounts provided by :man-pages:`pam_systemd_home(8)` do), but this parameter may be used to define a default if that's not provided.

   Note that this only adjusts :systemd:var:`$HOME` during login, it does not affect the otherwise reported home directory of the user. Specifically this means that :man-pages:`sshd(8)` will continue to look for SSH keys of the user only in the primary home directory of the user, not in any of their areas.

   Note that the default area to log into can also be configured as part of the user account. The area specified via :systemd:var:`area=` overrides the default area configured there. Also note that if the area is specified explicitly by the user at login time, it overrides both. Also note that setting this parameter to an empty string has the effect of undoing the effect of any default area configured as part of the user record, i.e. ensuring the user logs into the primary home directory of their account.

   For details on the area concept see :man-pages:`pam_systemd_home(8)`.

   .. versionadded:: 258

.. systemd:option:: default-capability-bounding-set=, default-capability-ambient-set=
   :group: pam-directives

   Takes a comma-separated list of process capabilities (e.g. :systemd:constant:`CAP_WAKE_ALARM`, :systemd:constant:`CAP_BLOCK_SUSPEND`, …) to set for the invoked session's processes, if the user record does not encode appropriate sets of capabilities directly. See :man-pages:`capabilities(7)` for details on the capabilities concept. If not specified, the default bounding set is left as is (i.e. usually contains the full set of capabilities). The default ambient set is set to :systemd:constant:`CAP_WAKE_ALARM` for regular users if the PAM session is associated with a local seat or if it is invoked for the systemd user service :code:`user@.service`. Otherwise, defaults to the empty set.

   .. versionadded:: 254

.. systemd:option:: debug[=]
   :group: pam-directives

   Takes an optional boolean argument. If yes or without the argument, the module will log debugging information as it operates.

Module Types Provided
#####################

Only :code:`session` is provided.

Environment
###########

The following environment variables are initialized by the module and available to the processes of the user's session:

.. systemd:var:: $XDG_SESSION_ID
   :group: environment-variables

   A short session identifier, suitable to be used in filenames. The string itself should be considered opaque, although often it is just the audit session ID as reported by :code:`/proc/self/sessionid`. Each ID will be assigned only once during machine uptime. It may hence be used to uniquely label files or other resources of this session. Combine this ID with the boot identifier, as returned by :ref:`sd_id128_get_boot(3)`, for a globally unique identifier.

.. systemd:var:: $XDG_RUNTIME_DIR
   :group: environment-variables

   Path to a user-private user-writable directory that is bound to the user login time on the machine. It is automatically created the first time a user logs in and removed on the user's final logout. If a user logs in twice at the same time, both sessions will see the same :systemd:var:`$XDG_RUNTIME_DIR` and the same contents. If a user logs in once, then logs out again, and logs in again, the directory contents will have been lost in between, but applications should not rely on this behavior and must be able to deal with stale files. To store session-private data in this directory, the user should include the value of :systemd:var:`$XDG_SESSION_ID` in the filename. This directory shall be used for runtime file system objects such as :systemd:constant:`AF_UNIX` sockets, FIFOs, PID files and similar. It is guaranteed that this directory is local and offers the greatest possible file system feature set the operating system provides. For further details, see the `XDG Base Directory Specification <https://standards.freedesktop.org/basedir-spec/basedir-spec-latest.html>`_. :systemd:var:`$XDG_RUNTIME_DIR` is not set if the current user is not the original user of the session.

.. systemd:var:: $TZ, $EMAIL, $LANG
   :group: environment-variables

   If a JSON user record is known for the user logging in these variables are initialized from the respective data in the record.

   .. versionadded:: 245

.. systemd:var:: $SHELL_PROMPT_PREFIX, $SHELL_PROMPT_SUFFIX, $SHELL_WELCOME
   :group: environment-variables

   These environment variables are initialized from the service credentials "shell.prompt.prefix", "shell.prompt.suffix" and "shell.welcome" if set. They are passed to the invoked session processes, where they are imported into any shell prompt (specifically :systemd:var:`$SHELL_PROMPT_PREFIX` is added as prefix to :systemd:var:`$PS1`, and :systemd:var:`$SHELL_PROMPT_SUFFIX` as suffix) or printed on screen when a shell first initializes.

   .. versionadded:: 257

The following environment variables are read by the module and may be used by the PAM service to pass metadata to the module. If these variables are not set when the PAM module is invoked but can be determined otherwise they are set by the module, so that these variables are initialized for the session and applications if known at all.

.. systemd:var:: $XDG_SESSION_TYPE
   :group: environment-variables

   The session type. This may be used instead of :systemd:var:`type=` on the module parameter line, and is usually preferred.

   .. versionadded:: 209

.. systemd:var:: $XDG_SESSION_CLASS
   :group: environment-variables

   The session class. This may be used instead of :systemd:var:`class=` on the module parameter line, and is usually preferred.

   .. versionadded:: 209

.. systemd:var:: $XDG_SESSION_DESKTOP
   :group: environment-variables

   The desktop identifier. This may be used instead of :systemd:var:`desktop=` on the module parameter line, and is usually preferred.

   .. versionadded:: 209

.. systemd:var:: $XDG_SEAT
   :group: environment-variables

   The seat name the session shall be registered for, if any.

   .. versionadded:: 209

.. systemd:var:: $XDG_VTNR
   :group: environment-variables

   The VT number the session shall be registered for, if any. (Only applies to seats with a VT available, such as "seat0")

   .. versionadded:: 209

.. systemd:var:: $XDG_AREA
   :group: environment-variables

   If an area (secondary home directories of the user, within the primary home directory) to log into has been selected this variable is set to the area name (without any path prefix). It is otherwise unset. For details about areas, see above.

   .. versionadded:: 258

If not set, :code:`pam_systemd` will initialize :code:`$XDG_SEAT` and :code:`$XDG_VTNR` based on the :code:`$DISPLAY` variable (if the latter is set).

Session limits
##############

PAM modules earlier in the stack, that is those that come before :code:`pam_systemd.so`, can set session scope limits using the PAM context objects. The data for these objects is provided as :code:`NUL`-terminated C strings and maps directly to the respective unit resource control directives. Note that these limits apply to individual sessions of the user, they do not apply to all user processes as a combined whole. In particular, the per-user :code:`user@.service` unit instance, which runs the :code:`systemd --user` manager process and its children, and is tracked outside of any session, being shared by all the user's sessions, is not covered by these limits.

See :ref:`systemd.resource-control(5)` for more information about the resources. Also, see :man-pages:`pam_set_data(3)` for additional information about how to set the context objects.

.. systemd:option:: systemd.memory_max=
   :group: pam-directives

   Sets unit :systemd:var:`MemoryMax=`.

   .. versionadded:: 239

.. systemd:option:: systemd.tasks_max=
   :group: pam-directives

   Sets unit :systemd:var:`TasksMax=`.

   .. versionadded:: 239

.. systemd:option:: systemd.cpu_weight=
   :group: pam-directives

   Sets unit :systemd:var:`CPUWeight=`.

   .. versionadded:: 239

.. systemd:option:: systemd.io_weight=
   :group: pam-directives

   Sets unit :systemd:var:`IOWeight=`.

   .. versionadded:: 239

.. systemd:option:: systemd.runtime_max_sec=
   :group: pam-directives

   Sets unit :systemd:var:`RuntimeMaxSec=`.

   .. versionadded:: 244

Example data as can be provided from an another PAM module:

.. code-block:: sh

   pam_set_data(handle, "systemd.memory_max", (void *)"200M", cleanup);
   pam_set_data(handle, "systemd.tasks_max",  (void *)"50",   cleanup);
   pam_set_data(handle, "systemd.cpu_weight", (void *)"100",  cleanup);
   pam_set_data(handle, "systemd.io_weight",  (void *)"340",  cleanup);
   pam_set_data(handle, "systemd.runtime_max_sec", (void *)"3600", cleanup);

Example
#######

Here's an example PAM configuration fragment that allows users sessions to be managed by :code:`systemd-logind.service`:

.. code-block:: sh

   #%PAM-1.0
   -auth     [success=done authtok_err=bad perm_denied=bad maxtries=bad default=ignore] pam_systemd_home.so
   auth      sufficient pam_unix.so
   auth      required   pam_deny.so
   account   required   pam_nologin.so
   -account  [success=done authtok_expired=bad new_authtok_reqd=bad maxtries=bad acct_expired=bad default=ignore] pam_systemd_home.so
   account   required   pam_unix.so
   -password sufficient pam_systemd_home.so
   password  sufficient pam_unix.so sha512 shadow try_first_pass
   password  required   pam_deny.so
   -session  optional   pam_keyinit.so revoke
   -session  optional   pam_loginuid.so
   -session  optional   pam_systemd_home.so
   -session  optional   pam_systemd.so
   session   required   pam_unix.so
