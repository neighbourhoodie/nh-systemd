systemd.net-naming-scheme(7)
============================

Name
####

systemd.net-naming-scheme — Network device naming schemes

Description
###########

Network interfaces names and MAC addresses may be generated based on certain stable interface attributes. This is possible when there is enough information about the device to generate those attributes and the use of this information is configured. This page describes interface naming, i.e. what possible names may be generated. Those names are generated by the :ref:`systemd-udevd.service(8)` builtin :code:`net_id` and exported as :man-pages:`udev(7)` properties (:code:`ID_NET_NAME_ONBOARD=`, :code:`ID_NET_LABEL_ONBOARD=`, :code:`ID_NET_NAME_PATH=`, :code:`ID_NET_NAME_SLOT=`).

Names and MAC addresses are derived from various stable device metadata attributes. Newer versions of :code:`systemd-udevd` take more of these attributes into account, improving (and thus possibly changing) the names and addresses used for the same devices. Different versions of those generation rules are called "naming schemes". The default naming scheme is chosen at compilation time. Usually this will be the latest implemented version, but it is also possible to set one of the older versions to preserve compatibility. This may be useful for example for distributions, which may introduce new versions of systemd in stable releases without changing the naming scheme. The naming scheme may also be overridden using the :code:`net.naming_scheme=` kernel command line switch, see :ref:`systemd-udevd.service(8)`. Available naming schemes are described below.

After the udev properties have been generated, appropriate udev rules may be used to actually rename devices based on those properties. See the description of :code:`NamePolicy=` and :code:`MACAddressPolicy=` in :ref:`systemd.link(5)`.

Note that while the concept of network interface naming schemes is primarily relevant in the context of :code:`systemd-udevd.service`, the :ref:`systemd-nspawn(1)` container manager also takes it into account when naming network interfaces, see below.

Policies
########

All names start with a two-character prefix that signifies the interface type.

.. list-table:: Two character prefixes based on the type of interface
   :header-rows: 1

   * - Prefix
     - Description
   * - :code:`en`
     - Ethernet
   * - :code:`ib`
     - InfiniBand
   * - :code:`sl`
     - Serial line IP (slip)
   * - :code:`wl`
     - Wireless local area network (WLAN)
   * - :code:`ww`
     - Wireless wide area network (WWAN)

The :man-pages:`udev(7)` :code:`net_id` builtin exports the following device properties:

.. systemd:option:: ID_NET_NAME_ONBOARD=prefixonumber, ID_NET_NAME_ONBOARD=prefixdnumber

   This name is set based on the numeric ordering information given by the firmware for on-board devices. Different schemes are used depending on the firmware type, as described in the table below.

   .. list-table:: On-board naming schemes
      :header-rows: 1

      * - Format
        - Description
      * - :emphasis:`prefix`:code:`o`:emphasis:`number`
        - PCI on-board index
      * - :emphasis:`prefix`:code:`d`:emphasis:`number`
        - DeviceTree alias index

   .. versionadded:: 243

.. systemd:option:: ID_NET_LABEL_ONBOARD=label

   This property is set based on textual label given by the firmware for on-board devices. This is only available for PCI devices.

   .. versionadded:: 243

.. systemd:option:: ID_NET_NAME_MAC=prefixxAABBCCDDEEFF

   This name consists of the prefix, letter :code:`x`, and 12 hexadecimal digits of the MAC address. It is available if the device has a fixed MAC address. Because this name is based on an attribute of the card itself, it remains "stable" when the device is moved (even between machines), but will change when the hardware is replaced.

   .. versionadded:: 243

.. systemd:option:: ID_NET_NAME_SLOT=prefix[Pdomain]sslot[ffunction][nport_name|ddev_port], ID_NET_NAME_SLOT=prefixvslot, ID_NET_NAME_SLOT=prefixxslot, ID_NET_NAME_SLOT=prefix[Pdomain]sslot[ffunction][nport_name|ddev_port]bnumber, ID_NET_NAME_SLOT=prefix[Pdomain]sslot[ffunction][nport_name|ddev_port]uport…[cconfig][iinterface], ID_NET_NAME_SLOT=prefix[Pdomain]sslot[ffunction][nport_name|ddev_port]vslot, ID_NET_NAME_SLOT=prefix[Pdomain]sslot[ffunction][nport_name|ddev_port]rslot

   This property describes the slot position. Different schemes are used depending on the bus type, as described in the table below. In case of USB, BCMA, and SR-VIO devices, the full name consists of the prefix, PCI slot identifier, and USB or BCMA or SR-VIO slot identifier. The first two parts are denoted as "…" in the table below.

   .. list-table:: Slot naming schemes
      :header-rows: 1

      * - Format
        - Description
      * - :emphasis:`prefix` [:code:`P`:emphasis:`domain`] :code:`s`:emphasis:`slot` [:code:`f`:emphasis:`function`] [:code:`n`:emphasis:`port_name` | :code:`d`:emphasis:`dev_port`]
        - PCI slot number
      * - :emphasis:`prefix` :code:`v`:emphasis:`slot`
        - VIO slot number (IBM PowerVM)
      * - :emphasis:`prefix` :code:`X`:emphasis:`number`
        - VIF interface number (Xen)
      * - … :code:`b`:emphasis:`number`
        - Broadcom bus (BCMA) core number
      * - … :code:`u`:emphasis:`port`\… [:code:`c`:emphasis:`config`] [:code:`i`:emphasis:`interface`]
        - USB port number chain
      * - … :code:`v`:emphasis:`slot`
        - SR-VIO slot number
      * - … :code:`r`:emphasis:`slot`
        - SR-IOV slot number

   The PCI domain is only prepended when it is not 0. All multi-function PCI devices will carry the :code:`f`:emphasis:`function` number in the device name, including the function 0 device. For non-multi-function devices, the number is suppressed if 0. The port name :emphasis:`port_name` is used, or the port number :code:`d`:emphasis:`dev_port` if the name is not known.

   For BCMA devices, the core number is suppressed when 0.

   For USB devices the full chain of port numbers of hubs is composed. If the name gets longer than the maximum number of 15 characters, the name is not exported. The usual USB configuration number 1 and interface number 0 values are suppressed.

   SR-IOV virtual devices are named based on the name of the parent interface, with a suffix of :code:`v` and the virtual device number, with any leading zeros removed. The bus number is ignored.

   SR-IOV virtual device representors are named based on the name of the physical device interface, with a suffix of :code:`r` and the number of the virtual device that is linked to the particular representor, with any leading zeros removed. The physical port name and the bus number are ignored.

   In some configurations a parent PCI bridge of a given network controller may be associated with a slot. In such case we do not generate this device property to avoid possible naming conflicts.

   .. versionadded:: 243

.. systemd:option:: ID_NET_NAME_PATH=prefixcbus_id, ID_NET_NAME_PATH=prefixavendormodeliinstance, ID_NET_NAME_PATH=prefixiaddressnport_name, ID_NET_NAME_PATH=prefixuport…, ID_NET_NAME_PATH=prefix[Pdomain]pbussslot[ffunction][nphys_port_name|ddev_port], ID_NET_NAME_PATH=prefix[Pdomain]pbussslot[ffunction][nphys_port_name|ddev_port]bnumber, ID_NET_NAME_PATH=prefix[Pdomain]pbussslot[ffunction][nphys_port_name|ddev_port]uport…[cconfig][iinterface]

   This property describes the device installation location. Different schemes are used depending on the bus type, as described in the table below. For BCMA and USB devices, PCI path information must known, and the full name consists of the prefix, PCI slot identifier, and USB or BCMA location. The first two parts are denoted as "…" in the table below.

   .. list-table:: Path naming schemes
      :header-rows: 1

      * - Format
        - Description
      * - :emphasis:`prefix` :code:`c`:emphasis:`bus_id`
        - CCW or grouped CCW device identifier
      * - :emphasis:`prefix` :code:`a`:emphasis:`vendor` :emphasis:`model` :code:`i`:emphasis:`instance`
        - ACPI path names for ARM64 platform devices
      * - :emphasis:`prefix` :code:`i`:emphasis:`address` :code:`n`:emphasis:`port_name`
        - Netdevsim (simulated networking device) device number and port name
      * - :emphasis:`prefix` [:code:`P`:emphasis:`domain`] :code:`p`:emphasis:`bus` :code:`s`:emphasis:`slot` [:code:`f`:emphasis:`function`] [:code:`n`:emphasis:`phys_port_name` | :code:`d`:emphasis:`dev_port`]
        - PCI geographical location
      * - … :code:`b`:emphasis:`number`
        - Broadcom bus (BCMA) core number
      * - … :code:`u`:emphasis:`port`\… [:code:`c`:emphasis:`config`] [:code:`i`:emphasis:`interface`]
        - USB port number chain

   CCW and grouped CCW devices are found in IBM System Z mainframes. Any leading zeros and dots are suppressed.

   For PCI, BCMA, and USB devices, the same rules as described above for slot naming are used.

   .. versionadded:: 243

History
#######

The following "naming schemes" have been defined (which may be chosen at system boot-up time via the :code:`net.naming_scheme=` kernel command line switch, see above):

.. systemd:option:: v238

   This is the naming scheme that was implemented in systemd 238.

   .. versionadded:: 243

.. systemd:option:: v239

   Naming was changed for virtual network interfaces created with SR-IOV and NPAR and for devices where the PCI network controller device does not have a slot number associated.

   SR-IOV virtual devices are named based on the name of the parent interface, with a suffix of "v:emphasis:`port`", where :emphasis:`port` is the virtual device number. Previously those virtual devices were named as if completely independent.

   The ninth and later NPAR virtual devices are named following the scheme used for the first eight NPAR partitions. Previously those devices were not renamed and the kernel default ("eth:emphasis:`N`") was used.

   Names are also generated for PCI devices where the PCI network controller device does not have an associated slot number itself, but one of its parents does. Previously those devices were not renamed and the kernel default was used.

   .. versionadded:: 243

.. systemd:option:: v240

   The "ib" prefix and stable names for infiniband devices are introduced. Previously those devices were not renamed.

   The ACPI index field (used in :code:`ID_NET_NAME_ONBOARD=`) is now also used when 0.

   A new naming policy :code:`NamePolicy=keep` was introduced. With this policy, if the network device name was already set by userspace, the device will not be renamed again. Previously, this naming policy applied implicitly, and now it must be explicitly requested. Effectively, this means that network devices will be renamed according to the configuration, even if they have been renamed already, if :code:`keep` is not specified as the naming policy in the :code:`.link` file. See :ref:`systemd.link(5)` for a description of :code:`NamePolicy=`.

   .. versionadded:: 243

.. systemd:option:: v241

   :code:`MACAddressPolicy=persistent` was extended to set MAC addresses based on the device name. Previously addresses were only based on the :code:`ID_NET_NAME_*` attributes, which meant that interface names would never be generated for virtual devices. Now a persistent address will be generated for most devices, including in particular bridges.

   Note: when userspace does not set a MAC address for a bridge device, the kernel will initially assign a random address, and then change it when the first device is enslaved to the bridge. With this naming policy change, bridges get a persistent MAC address based on the bridge name instead of the first enslaved device.

   .. versionadded:: 243

.. systemd:option:: v243

   Support for renaming netdevsim (simulated networking) devices was added. Previously those devices were not renamed.

   Previously two-letter interface type prefix was prepended to :code:`ID_NET_LABEL_ONBOARD=`. This is not done anymore.

   .. versionadded:: 243

.. systemd:option:: v245

   When :ref:`systemd-nspawn(1)` derives the name for the host side of the network interface created with :code:`--network-veth` from the container name it previously simply truncated the result at 15 characters if longer (since that's the maximum length for network interface names). From now on, for any interface name that would be longer than 15 characters the last 4 characters are set to a 24bit hash value of the full interface name. This way network interface name collisions between multiple similarly named containers (who only differ in container name suffix) should be less likely (but still possible, since the 24bit hash value is very small).

   .. versionadded:: 245

.. systemd:option:: v247

   When a PCI slot is associated with a PCI bridge that has multiple child network controllers, the same value of the :code:`ID_NET_NAME_SLOT` property might be derived for those controllers. This would cause a naming conflict if the property is selected as the device name. Now, we detect this situation and do not produce the :code:`ID_NET_NAME_SLOT` property.

   .. versionadded:: 247

.. systemd:option:: v249

   PCI hotplug slot names for the s390 PCI driver are a hexadecimal representation of the :code:`function_id` device attribute. This attribute is now used to build the :code:`ID_NET_NAME_SLOT`. Before that, all slot names were parsed as decimal numbers, which could either result in an incorrect value of the :code:`ID_NET_NAME_SLOT` property or none at all.

   Some firmware and hypervisor implementations report unreasonably high numbers for the on-board index. To prevent the generation of bogus on-board interface names, index numbers greater than 16381 (2¹⁴-1) were ignored. For s390 PCI devices index values up to 65535 (2¹⁶-1) are valid. To account for that, the limit was increased to 65535.

   The :man-pages:`udev(7)` rule :code:`NAME=` replaces ":", "/", and "%" with an underscore ("_"), and refuses strings which contain only digits.

   .. versionadded:: 249

.. systemd:option:: v250

   Added naming scheme for Xen netfront "vif" interfaces based on the guest side VIF number set from the Xen config (or the interface index in AWS EC2).

   .. versionadded:: 250

.. systemd:option:: v251

   Since version :code:`v247` we no longer set :code:`ID_NET_NAME_SLOT` if we detect that a PCI device associated with a slot is a PCI bridge as that would create naming conflict when there are more child devices on that bridge. Now, this is relaxed and we will use slot information to generate the name based on it but only if the PCI device has multiple functions. This is safe because distinct function number is a part of the device name for multifunction devices. Note, this is reverted in :code:`v255`. See below.

   .. versionadded:: 251

.. systemd:option:: v252

   Added naming scheme for platform devices with devicetree aliases.

   .. versionadded:: 252

.. systemd:option:: v253

   Set :code:`ID_NET_NAME_PATH` for usb devices not connected via a PCI bus.

   .. versionadded:: 253

.. systemd:option:: v254

   Naming was changed for SR-IOV virtual device representors, optionally settable at compilation time. The "r:emphasis:`slot`" suffix was added to differentiate SR-IOV virtual device representors attached to a single physical device interface. Because of a mistake, this scheme was *not the default scheme for systemd version 254*\..

   .. versionadded:: 255

.. systemd:option:: v255

   Naming was changed for SR-IOV virtual device representors to enable the change introduced in :code:`v254` by default.

   If we detect that a PCI device associated with a slot is a PCI bridge, we no longer set :code:`ID_NET_NAME_SLOT`, reverting a change that was introduced in :code:`v251`.

   .. versionadded:: 255

.. systemd:option:: v257

   PCI slot number is now read from :code:`firmware_node/sun` sysfs file.

   The naming scheme based on devicetree aliases was extended to support aliases for individual interfaces of controllers with multiple ports.

   .. versionadded:: 257

.. systemd:option:: v258

   When no renaming is requested, :code:`ID_NET_NAME` property is now equivalent to :code:`INTERFACE` property.

   .. versionadded:: 258

.. systemd:option:: v259

   The naming scheme based on devicetree aliases was extended to support WLAN devices.

   .. versionadded:: 259

Note that :code:`latest` may be used to denote the latest scheme known (to this particular version of systemd).

Limiting the use of specific sysfs attributes
#############################################

When creating names for network cards, some naming schemes use data from sysfs populated by the kernel. This means that although a specific naming scheme in :man-pages:`udev(7)` is picked, the network card's name can still change when a new kernel version adds a new sysfs attribute. For example, if kernel starts setting the :code:`phys_port_name`, :code:`udev` will append the ":code:`n`:emphasis:`phys_port_name`" suffix to the device name.

.. systemd:constant:: ID_NET_NAME_ALLOW=BOOL

   This udev property sets a fallback policy for reading a sysfs attribute. If set to :code:`0` udev will not read any sysfs attribute by default, unless it is explicitly allowlisted, see below. If set to :code:`1` udev can use any sysfs attribute unless it is explicitly forbidden. The default value is :code:`1`.

   .. versionadded:: 256

.. systemd:option:: ID_NET_NAME_ALLOW_sysfsattr=BOOL

   This udev property explicitly states if udev shall use the specified :emphasis:`sysfsattr`, when composing the device name.

   .. versionadded:: 256

With these options, users can set an allowlist or denylist for sysfs attributes. To create an allowlist, the user needs to set :code:`ID_NET_NAME_ALLOW=0` for the device and then list the allowed attributes with the :code:`ID_NET_NAME_ALLOW_:emphasis:`sysfsattr`\=1` options. In case of a denylist, the user needs to provide the list of denied attributes with the :code:`ID_NET_NAME_ALLOW_:emphasis:`sysfsattr`\=0` options.

Examples
########

Using :code:`udevadm test-builtin` to display device properties
---------------------------------------------------------------

.. code-block:: sh

   $ udevadm test-builtin net_id /sys/class/net/enp0s31f6
   ...
   Using default interface naming scheme 'v243'.
   ID_NET_NAMING_SCHEME=v243
   ID_NET_NAME_MAC=enx54ee75cb1dc0
   ID_OUI_FROM_DATABASE=Wistron InfoComm(Kunshan)Co.,Ltd.
   ID_NET_NAME_PATH=enp0s31f6
   ...

PCI Ethernet card with firmware index "1"
-----------------------------------------

.. code-block:: sh

   ID_NET_NAME_ONBOARD=eno1
   ID_NET_NAME_ONBOARD_LABEL=Ethernet Port 1

PCI Ethernet card in slot with firmware index number
----------------------------------------------------

.. code-block:: sh

   # /sys/devices/pci0000:00/0000:00:1c.3/0000:05:00.0/net/ens1
   ID_NET_NAME_MAC=enx000000000466
   ID_NET_NAME_PATH=enp5s0
   ID_NET_NAME_SLOT=ens1

PCI Ethernet multi-function card with 2 ports
---------------------------------------------

.. code-block:: sh

   # /sys/devices/pci0000:00/0000:00:1c.0/0000:02:00.0/net/enp2s0f0
   ID_NET_NAME_MAC=enx78e7d1ea46da
   ID_NET_NAME_PATH=enp2s0f0
   # /sys/devices/pci0000:00/0000:00:1c.0/0000:02:00.1/net/enp2s0f1
   ID_NET_NAME_MAC=enx78e7d1ea46dc
   ID_NET_NAME_PATH=enp2s0f1

PCI WLAN card
-------------

.. code-block:: sh

   # /sys/devices/pci0000:00/0000:00:1c.1/0000:03:00.0/net/wlp3s0
   ID_NET_NAME_MAC=wlx0024d7e31130
   ID_NET_NAME_PATH=wlp3s0

PCI IB host adapter with 2 ports
--------------------------------

.. code-block:: sh

   # /sys/devices/pci0000:00/0000:00:03.0/0000:15:00.0/net/ibp21s0f0
   ID_NET_NAME_PATH=ibp21s0f0
   # /sys/devices/pci0000:00/0000:00:03.0/0000:15:00.1/net/ibp21s0f1
   ID_NET_NAME_PATH=ibp21s0f1

USB built-in 3G modem
---------------------

.. code-block:: sh

   # /sys/devices/pci0000:00/0000:00:1d.0/usb2/2-1/2-1.4/2-1.4:1.6/net/wwp0s29u1u4i6
   ID_NET_NAME_MAC=wwx028037ec0200
   ID_NET_NAME_PATH=wwp0s29u1u4i6

USB Android phone
-----------------

.. code-block:: sh

   # /sys/devices/pci0000:00/0000:00:1d.0/usb2/2-1/2-1.2/2-1.2:1.0/net/enp0s29u1u2
   ID_NET_NAME_MAC=enxd626b3450fb5
   ID_NET_NAME_PATH=enp0s29u1u2

s390 grouped CCW interface
--------------------------

.. code-block:: sh

   # /sys/devices/css0/0.0.0007/0.0.f5f0/group_device/net/encf5f0
   ID_NET_NAME_MAC=enx026d3c00000a
   ID_NET_NAME_PATH=encf5f0

Set an allowlist for reading sysfs attributes for network card naming
---------------------------------------------------------------------

.. code-block:: sh

   /etc/udev/hwdb.d/50-net-naming-allowlist.hwdb
   net:naming:drvirtio_net:*
     ID_NET_NAME_ALLOW=0
     ID_NET_NAME_ALLOW_ACPI_INDEX=1
     ID_NET_NAME_ALLOW_ADDR_ASSIGN_TYPE=1
     ID_NET_NAME_ALLOW_ADDRESS=1
     ID_NET_NAME_ALLOW_ARI_ENABLED=1
     ID_NET_NAME_ALLOW_DEV_PORT=1
     ID_NET_NAME_ALLOW_FUNCTION_ID=1
     ID_NET_NAME_ALLOW_IFLINK=1
     ID_NET_NAME_ALLOW_INDEX=1
     ID_NET_NAME_ALLOW_LABEL=1
     ID_NET_NAME_ALLOW_PHYS_PORT_NAME=1
     ID_NET_NAME_ALLOW_TYPE=1

Set a denylist so that specified sysfs attribute are ignored
------------------------------------------------------------

.. code-block:: sh

   /etc/udev/hwdb.d/50-net-naming-denylist.hwdb
   net:naming:drvirtio_net:*
     ID_NET_NAME_ALLOW=1
     ID_NET_NAME_ALLOW_DEV_PORT=0
     ID_NET_NAME_ALLOW_PHYS_PORT_NAME=0
