==========
systemd(1)
==========

Name
####

systemd, init — systemd system and service manager

Synopsis
########

:code:`/usr/lib/systemd/systemd [OPTIONS...]`

:code:`init [OPTIONS...]`

Description
###########

systemd is a system and service manager for Linux operating systems. When run as first process on boot (as PID 1), it acts as init system that brings up and maintains userspace services. Separate instances are started for logged-in users to start their services.

:code:`systemd` is usually not invoked directly by the user, but is installed as the :code:`/sbin/init` symlink and started during early boot. The user manager instances are started automatically through the :man-pages:`user@.service(5)` service.

When run as a system instance, systemd interprets the configuration file :code:`system.conf` and the files in :code:`system.conf.d` directories; when run as a user instance, systemd interprets the configuration file :code:`user.conf` and the files in :code:`user.conf.d` directories. See :ref:`systemd-system.conf(5)` for more information.

:code:`systemd` contains native implementations of various tasks that need to be executed as part of the boot process. For example, it sets the hostname or configures the loopback network device. It also sets up and mounts various API file systems, such as :code:`/sys/`, :code:`/proc/`, and :code:`/dev/`.

:code:`systemd` will also reset the system clock during early boot if it appears to be set incorrectly. See "System clock epoch" section below.

Note that some but not all interfaces provided by systemd are covered by the `Interface Portability and Stability Promise <https://systemd.io/PORTABILITY_AND_STABILITY/>`_.

The D-Bus API of :code:`systemd` is described in :man-pages:`org.freedesktop.systemd1(5)` and :man-pages:`org.freedesktop.LogControl1(5)`.

Systems which invoke systemd in a container or initrd environment should implement the `Container Interface <https://systemd.io/CONTAINER_INTERFACE>`_ or `initrd Interface <https://systemd.io/INITRD_INTERFACE/>`_ specifications, respectively.

Units
#####

systemd provides a dependency system between various entities called "units" of 11 different types. Units encapsulate various objects that are relevant for system boot-up and maintenance. The majority of units are configured in unit configuration files, whose syntax and basic set of options is described in :ref:`systemd.unit(5)`, however some are created automatically from other configuration files, dynamically from system state or programmatically at runtime. Units may be in a number of states, described in the following table. Note that the various unit types may have a number of additional substates, which are mapped to the generalized unit states described here.

.. include:: unit-states.rst
    :start-after: .. inclusion-marker-do-not-remove table|
    :end-before: .. inclusion-end-marker-do-not-remove table|

The following unit types are available:

1.    Service units, which start and control daemons and the processes they consist of. For details, see :ref:`systemd.service(5)`.

2.    Socket units, which encapsulate local IPC or network sockets in the system, useful for socket-based activation. For details about socket units, see :ref:`systemd.socket(5)`, for details on socket-based activation and other forms of activation, see :man-pages:`daemon(7)`.

3.    Target units are useful to group units, or provide well-known synchronization points during boot-up, see :ref:`systemd.target(5)`.

4.    Device units expose kernel devices in systemd and may be used to implement device-based activation. For details, see :ref:`systemd.device(5)`.

5.    Mount units control mount points in the file system, for details see :ref:`systemd.mount(5)`.

6.    Automount units provide automount capabilities, for on-demand mounting of file systems as well as parallelized boot-up. See :ref:`systemd.automount(5)`.

7.    Timer units are useful for triggering activation of other units based on timers. You may find details in :ref:`systemd.timer(5)`.

8.    Swap units are very similar to mount units and encapsulate memory swap partitions or files of the operating system. They are described in :ref:`systemd.swap(5)`.

9.    Path units may be used to activate other services when file system objects change or are modified. See :ref:`systemd.path(5)`.

10.    Slice units may be used to group units which manage system processes (such as service and scope units) in a hierarchical tree for resource management purposes. See :ref:`systemd.slice(5)`.

11.    Scope units are similar to service units, but manage foreign processes instead of starting them as well. See :ref:`systemd.scope(5)`.

Units are named as their configuration files. Some units have special semantics. A detailed list is available in :ref:`systemd.special(7)`.

systemd knows various kinds of dependencies, including positive and negative requirement dependencies (i.e. :code:`Requires=` and :code:`Conflicts=`) as well as ordering dependencies (:code:`After=` and :code:`Before=`). NB: ordering and requirement dependencies are orthogonal. If only a requirement dependency exists between two units (e.g. :code:`foo.service` requires :code:`bar.service`), but no ordering dependency (e.g. :code:`foo.service` after :code:`bar.service`) and both are requested to start, they will be started in parallel. It is a common pattern that both requirement and ordering dependencies are placed between two units. Also note that the majority of dependencies are implicitly created and maintained by systemd. In most cases, it should be unnecessary to declare additional dependencies manually, however it is possible to do this.

Application programs and units (via dependencies) may request state changes of units. In systemd, these requests are encapsulated as 'jobs' and maintained in a job queue. Jobs may succeed or can fail, their execution is ordered based on the ordering dependencies of the units they have been scheduled for.

On boot systemd activates the target unit :code:`default.target` whose job is to activate on-boot services and other on-boot units by pulling them in via dependencies. Usually, the unit name is just an alias (symlink) for either :code:`graphical.target` (for fully-featured boots into the UI) or :code:`multi-user.target` (for limited console-only boots for use in embedded or server environments, or similar; a subset of graphical.target). However, it is at the discretion of the administrator to configure it as an alias to any other target unit. See :ref:`systemd.special(7)` for details about these target units.

On first boot, :code:`systemd` will enable or disable units according to preset policy. See :ref:`systemd.preset(5)` and "First Boot Semantics" in :man-pages:`machine-id(5)`.

systemd only keeps a minimal set of units loaded into memory. Specifically, the only units that are kept loaded into memory are those for which at least one of the following conditions is true:

1.    It is in an active, activating, deactivating or failed state (i.e. in any unit state except for "inactive")

2.    It has a job queued for it

3.    It is a dependency of at least one other unit that is loaded into memory

4.    It has some form of resource still allocated (e.g. a service unit that is inactive but for which a process is still lingering that ignored the request to be terminated)

5.    It has been pinned into memory programmatically by a D-Bus call

systemd will automatically and implicitly load units from disk — if they are not loaded yet — as soon as operations are requested for them. Thus, in many respects, the fact whether a unit is loaded or not is invisible to clients. Use :code:`systemctl list-units --all` to comprehensively list all units currently loaded. Any unit for which none of the conditions above applies is promptly unloaded. Note that when a unit is unloaded from memory its accounting data is flushed out too. However, this data is generally not lost, as a journal log record is generated declaring the consumed resources whenever a unit shuts down.

Processes systemd spawns are placed in individual Linux control groups named after the unit which they belong to in the private systemd hierarchy. (see `Control Groups v2 <https://docs.kernel.org/admin-guide/cgroup-v2.html>`_ for more information about control groups, or short "cgroups"). systemd uses this to effectively keep track of processes. Control group information is maintained in the kernel, and is accessible via the file system hierarchy (beneath :code:`/sys/fs/cgroup/`), or in tools such as :man-pages:`systemd-cgls(1)` or :man-pages:`ps(1)` (:code:`ps xawf -eo pid,user,cgroup,args` is particularly useful to list all processes and the systemd units they belong to.).

systemd is compatible with various established Unix functionality such as :code:`/etc/fstab` or the :code:`utmp` database.

systemd has a minimal transaction system: if a unit is requested to start up or shut down it will add it and all its dependencies to a temporary transaction. Then, it will verify if the transaction is consistent (i.e. whether the ordering of all units is cycle-free). If it is not, systemd will try to fix it up, and removes non-essential jobs from the transaction that might remove the loop. Also, systemd tries to suppress non-essential jobs in the transaction that would stop a running service. Finally it is checked whether the jobs of the transaction contradict jobs that have already been queued, and optionally the transaction is aborted then. If all worked out and the transaction is consistent and minimized in its impact it is merged with all already outstanding jobs and added to the run queue. Effectively this means that before executing a requested operation, systemd will verify that it makes sense, fixing it if possible, and only failing if it really cannot work.

Note that transactions are generated independently of a unit's state at runtime, hence, for example, if a start job is requested on an already started unit, it will still generate a transaction and wake up any inactive dependencies (and cause propagation of other jobs as per the defined relationships). This is because the enqueued job is at the time of execution compared to the target unit's state and is marked successful and complete when both satisfy. However, this job also pulls in other dependencies due to the defined relationships and thus leads to, in our example, start jobs for any of those inactive units getting queued as well.

Units may be generated dynamically at boot and system manager reload time, for example based on other configuration files or parameters passed on the kernel command line. For details, see :ref:`systemd.generator(7)`.

Directories
###########

.. systemd:option:: System unit directories

   The systemd system manager reads unit configuration from various directories. Packages that want to install unit files shall place them in the directory returned by :code:`pkg-config systemd --variable=systemdsystemunitdir`. Other directories checked are :code:`/usr/local/lib/systemd/system` and :code:`/usr/lib/systemd/system`. User configuration always takes precedence. :code:`pkg-config systemd --variable=systemdsystemconfdir` returns the path of the system configuration directory. Packages should alter the content of these directories only with the :code:`enable` and :code:`disable` commands of the :man-pages:`systemctl(1)` tool. Full list of directories is provided in :ref:`systemd.unit(5)`.

.. systemd:option:: User unit directories

   Similar rules apply for the user unit directories. However, here the `XDG Base Directory specification <https://standards.freedesktop.org/basedir-spec/basedir-spec-latest.html>`_ is followed to find units. Applications should place their unit files in the directory returned by :code:`pkg-config systemd --variable=systemduserunitdir`. Global configuration is done in the directory reported by :code:`pkg-config systemd --variable=systemduserconfdir`. The :code:`enable` and :code:`disable` commands of the :man-pages:`systemctl(1)` tool can handle both global (i.e. for all users) and private (for one user) enabling/disabling of units. Full list of directories is provided in :ref:`systemd.unit(5)`.

Signals
#######

The service listens to various UNIX process signals that can be used to request various actions asynchronously. The signal handling is enabled very early during boot, before any further processes are invoked. However, a supervising container manager or similar that intends to request these operations via this mechanism must take into consideration that this functionality is not available during the earliest initialization phase. An :code:`sd_notify()` notification message carrying the :code:`X_SYSTEMD_SIGNALS_LEVEL=2` field is emitted once the signal handlers are enabled, see below. This may be used to schedule submission of these signals correctly.

.. systemd:constant:: SIGTERM

   Upon receiving this signal the systemd system manager serializes its state, reexecutes itself and deserializes the saved state again. This is mostly equivalent to :code:`systemctl daemon-reexec`.

   systemd user managers will start the :code:`exit.target` unit when this signal is received. This is mostly equivalent to :code:`systemctl --user start exit.target --job-mode=replace-irreversibly`.

.. systemd:constant:: SIGINT

   Upon receiving this signal the systemd system manager will start the :code:`ctrl-alt-del.target` unit. This is mostly equivalent to :code:`systemctl start ctrl-alt-del.target --job-mode=replace-irreversibly`. If this signal is received more than 7 times per 2s, an immediate reboot is triggered. Note that pressing :kbd:`Ctrl` + :kbd:`Alt` + :kbd:`Del` on the console will trigger this signal. Hence, if a reboot is hanging, pressing :kbd:`Ctrl` + :kbd:`Alt` + :kbd:`Del` more than 7 times in 2 seconds is a relatively safe way to trigger an immediate reboot.

   systemd user managers treat this signal the same way as :code:`SIGTERM`.

.. systemd:constant:: SIGWINCH

   When this signal is received the systemd system manager will start the :code:`kbrequest.target` unit. This is mostly equivalent to :code:`systemctl start kbrequest.target`.

   This signal is ignored by systemd user managers.

.. systemd:constant:: SIGPWR

   When this signal is received the systemd manager will start the :code:`sigpwr.target` unit. This is mostly equivalent to :code:`systemctl start sigpwr.target`.

.. systemd:constant:: SIGUSR1

   When this signal is received the systemd manager will try to reconnect to the D-Bus bus.

.. systemd:constant:: SIGUSR2

   When this signal is received the systemd manager will log its complete state in human-readable form. The data logged is the same as printed by :code:`systemd-analyze dump`.

.. systemd:constant:: SIGHUP

   Reloads the complete daemon configuration. This is mostly equivalent to :code:`systemctl daemon-reload`.

.. systemd:constant:: SIGRTMIN+0

   Enters default mode, starts the :code:`default.target` unit. This is mostly equivalent to :code:`systemctl isolate default.target`.

.. systemd:constant:: SIGRTMIN+1

   Enters rescue mode, starts the :code:`rescue.target` unit. This is mostly equivalent to :code:`systemctl isolate rescue.target`.

.. systemd:constant:: SIGRTMIN+2

   Enters emergency mode, starts the :code:`emergency.service` unit. This is mostly equivalent to :code:`systemctl isolate emergency.service`.

.. systemd:constant:: SIGRTMIN+3

   Halts the machine, starts the :code:`halt.target` unit. This is mostly equivalent to :code:`systemctl start halt.target --job-mode=replace-irreversibly`.

.. systemd:constant:: SIGRTMIN+4

   Powers off the machine, starts the :code:`poweroff.target` unit. This is mostly equivalent to :code:`systemctl start poweroff.target --job-mode=replace-irreversibly`.

.. systemd:constant:: SIGRTMIN+5

   Reboots the machine, starts the :code:`reboot.target` unit. This is mostly equivalent to :code:`systemctl start reboot.target --job-mode=replace-irreversibly`.

.. systemd:constant:: SIGRTMIN+6

   Reboots the machine via kexec, starts the :code:`kexec.target` unit. This is mostly equivalent to :code:`systemctl start kexec.target --job-mode=replace-irreversibly`.

.. systemd:constant:: SIGRTMIN+7

   Reboots userspace, starts the :code:`soft-reboot.target` unit. This is mostly equivalent to :code:`systemctl start soft-reboot.target --job-mode=replace-irreversibly`.

   .. versionadded:: 254

.. systemd:constant:: SIGRTMIN+13

   Immediately halts the machine.

.. systemd:constant:: SIGRTMIN+14

   Immediately powers off the machine.

.. systemd:constant:: SIGRTMIN+15

   Immediately reboots the machine.

.. systemd:constant:: SIGRTMIN+16

   Immediately reboots the machine with kexec.

.. systemd:constant:: SIGRTMIN+17

   Immediately reboots the userspace.

   .. versionadded:: 254

.. systemd:constant:: SIGRTMIN+20

   Enables display of status messages on the console, as controlled via :code:`systemd.show_status=1` on the kernel command line.

   You may want to use :code:`SetShowStatus()` instead of :code:`SIGRTMIN+20` in order to prevent race conditions. See :man-pages:`org.freedesktop.systemd1(5)`.

.. systemd:constant:: SIGRTMIN+21

   Disables display of status messages on the console, as controlled via :code:`systemd.show_status=0` on the kernel command line.

   You may want to use :code:`SetShowStatus()` instead of :code:`SIGRTMIN+21` in order to prevent race conditions. See :man-pages:`org.freedesktop.systemd1(5)`.

.. systemd:constant:: SIGRTMIN+22

   Sets the service manager's log level to "debug", in a fashion equivalent to :code:`systemd.log_level=debug` on the kernel command line.

.. systemd:constant:: SIGRTMIN+23

   Restores the log level to its configured value. The configured value is derived from – in order of priority – the value specified with :code:`systemd.log-level=` on the kernel command line, or the value specified with :code:`LogLevel=` in the configuration file, or the built-in default of "info".

   .. versionadded:: 239

.. systemd:constant:: SIGRTMIN+24

   Immediately exits the manager (only available for --user instances).

   .. versionadded:: 195

.. systemd:constant:: SIGRTMIN+25

   Upon receiving this signal the systemd manager will reexecute itself. This is mostly equivalent to :code:`systemctl daemon-reexec` except that it will be done asynchronously.

   The systemd system manager treats this signal the same way as :code:`SIGTERM`.

   .. versionadded:: 250

.. systemd:constant:: SIGRTMIN+26

   Restores the log target to its configured value. The configured value is derived from – in order of priority – the value specified with :code:`systemd.log-target=` on the kernel command line, or the value specified with :code:`LogTarget=` in the configuration file, or the built-in default.

   .. versionadded:: 239

.. systemd:constant:: SIGRTMIN+27, SIGRTMIN+28

   Sets the log target to "console" on :code:`SIGRTMIN+27` (or "kmsg" on :code:`SIGRTMIN+28`), in a fashion equivalent to :code:`systemd.log_target=console` (or :code:`systemd.log_target=kmsg` on :code:`SIGRTMIN+28`) on the kernel command line.

   .. versionadded:: 239

Environment
###########

The environment block for the system manager is initially set by the kernel. (In particular, "key=value" assignments on the kernel command line are turned into environment variables for PID 1). For the user manager, the system manager sets the environment as described in the "Environment Variables in Spawned Processes" section of :ref:`systemd.exec(5)`. The :code:`DefaultEnvironment=` setting in the system manager applies to all services including :code:`user@.service`. Additional entries may be configured (as for any other service) through the :code:`Environment=` and :code:`EnvironmentFile=` settings for :code:`user@.service` (see :ref:`systemd.exec(5)`). Also, additional environment variables may be set through the :code:`ManagerEnvironment=` setting in :ref:`systemd-system.conf(5)` and :ref:`systemd-user.conf(5)`.

Kernel Command Line
###################

When run as the system instance, systemd parses a number of options listed below. They can be specified as kernel command line arguments which are parsed from a number of sources depending on the environment in which systemd is executed. If run inside a Linux container, these options are parsed from the command line arguments passed to systemd itself, next to any of the command line options listed in the Options section above. If run outside of Linux containers, these arguments are parsed from :code:`/proc/cmdline` instead.

The following variables are understood:

.. systemd:option:: systemd.unit=, rd.systemd.unit=
   :group: kernel-commandline-options

   Overrides the unit to activate on boot. Defaults to :code:`default.target`. This may be used to temporarily boot into a different boot unit, for example :code:`rescue.target` or :code:`emergency.service`. See :ref:`systemd.special(7)` for details about these units. The option prefixed with "rd." is honored only in the initrd, while the one that is not prefixed only in the main system.

.. systemd:option:: systemd.dump_core
   :group: kernel-commandline-options

   Takes a boolean argument or enables the option if specified without an argument. If enabled, the systemd manager (PID 1) dumps core when it crashes. Otherwise, no core dump is created. Defaults to enabled.

   .. versionadded:: 233

.. systemd:option:: systemd.crash_chvt
   :group: kernel-commandline-options

   Takes a positive integer, or a boolean argument. Can be also specified without an argument, with the same effect as a positive boolean. If a positive integer (in the range 1–63) is specified, the system manager (PID 1) will activate the specified virtual terminal when it crashes. Defaults to disabled, meaning that no such switch is attempted. If set to enabled, the virtual terminal the kernel messages are written to is used instead.

   .. versionadded:: 233

.. systemd:option:: systemd.crash_shell
   :group: kernel-commandline-options

   Takes a boolean argument or enables the option if specified without an argument. If enabled, the system manager (PID 1) spawns a shell when it crashes. Otherwise, no shell is spawned. Defaults to disabled, for security reasons, as the shell is not protected by password authentication.

   .. versionadded:: 233

.. systemd:option:: systemd.crash_action=
   :group: kernel-commandline-options

   Takes one of "freeze", "reboot" or "poweroff". Defaults to "freeze". If set to "freeze", the system will hang indefinitely when the system manager (PID 1) crashes. If set to "reboot", the system manager (PID 1) will reboot the machine automatically when it crashes, after a 10s delay. If set to "poweroff", the system manager (PID 1) will power off the machine immediately when it crashes. If combined with :systemd:var:`systemd.crash_shell`, the configured crash action is executed after the shell exits.

   .. versionadded:: 256

.. systemd:option:: systemd.confirm_spawn
   :group: kernel-commandline-options

   Takes a boolean argument or a path to the virtual console where the confirmation messages should be emitted. Can be also specified without an argument, with the same effect as a positive boolean. If enabled, the system manager (PID 1) asks for confirmation when spawning processes using :systemd:option:`/dev/console`. If a path or a console name (such as "ttyS0") is provided, the virtual console pointed to by this path or described by the give name will be used instead. Defaults to disabled.

   .. versionadded:: 233

.. systemd:option:: systemd.service_watchdogs=
   :group: kernel-commandline-options

   Takes a boolean argument. If disabled, all service runtime watchdogs (:systemd:option:`WatchdogSec=`) and emergency actions (e.g. :systemd:option:`OnFailure=` or :systemd:option:`StartLimitAction=`) are ignored by the system manager (PID 1); see :ref:`systemd.service(5)`. Defaults to enabled, i.e. watchdogs and failure actions are processed normally. The hardware watchdog is not affected by this option.

   .. versionadded:: 237

.. systemd:option:: systemd.show_status
   :group: kernel-commandline-options

   Takes a boolean argument or the constants :systemd:constant:`error` and :systemd:constant:`auto`. Can be also specified without an argument, with the same effect as a positive boolean. If enabled, the systemd manager (PID 1) shows terse service status updates on the console during bootup. With :systemd:constant:`error`, only messages about failures are shown, but boot is otherwise quiet. :systemd:constant:`auto` behaves like :systemd:option:`false` until there is a significant delay in boot. Defaults to enabled, unless :systemd:option:`quiet` is passed as kernel command line option, in which case it defaults to :systemd:constant:`error`. If specified overrides the system manager configuration file option :systemd:option:`ShowStatus=`, see :ref:`systemd-system.conf(5)`.

   .. versionadded:: 233

.. systemd:option:: systemd.status_unit_format=
   :group: kernel-commandline-options

   Takes :systemd:option:`name`, :systemd:option:`description` or :systemd:option:`combined` as the value. If :systemd:option:`name`, the system manager will use unit names in status messages. If :systemd:option:`combined`, the system manager will use unit names and description in status messages. When specified, overrides the system manager configuration file option :systemd:option:`StatusUnitFormat=`, see :ref:`systemd-system.conf(5)`.

   .. versionadded:: 243

.. systemd:option:: systemd.log_color, systemd.log_level=, systemd.log_location, systemd.log_target=, systemd.log_time, systemd.log_tid, systemd.log_ratelimit_kmsg
   :group: kernel-commandline-options

   Controls log output, with the same effect as the :systemd:var:`$SYSTEMD_LOG_COLOR`, :systemd:var:`$SYSTEMD_LOG_LEVEL`, :systemd:var:`$SYSTEMD_LOG_LOCATION`, :systemd:var:`$SYSTEMD_LOG_TARGET`, :systemd:var:`$SYSTEMD_LOG_TIME`, :systemd:var:`$SYSTEMD_LOG_TID` and :systemd:var:`$SYSTEMD_LOG_RATELIMIT_KMSG` environment variables described above. :systemd:var:`systemd.log_color`, :systemd:var:`systemd.log_location`, :systemd:var:`systemd.log_time`, :systemd:var:`systemd.log_tid` and :systemd:var:`systemd.log_ratelimit_kmsg` can be specified without an argument, with the same effect as a positive boolean.

.. systemd:option:: systemd.default_standard_output=, systemd.default_standard_error=
   :group: kernel-commandline-options

   Controls default standard output and error output for services and sockets. That is, controls the default for :systemd:option:`StandardOutput=` and :systemd:option:`StandardError=` (see :ref:`systemd.exec(5)` for details). Takes one of :systemd:option:`inherit`, :systemd:option:`null`, :systemd:option:`tty`, :systemd:option:`journal`, :systemd:option:`journal+console`, :systemd:option:`kmsg`, :systemd:option:`kmsg+console`. If the argument is omitted :systemd:var:`systemd.default-standard-output=` defaults to :systemd:option:`journal` and :systemd:var:`systemd.default-standard-error=` to :systemd:option:`inherit`.

.. systemd:option:: systemd.setenv=
   :group: kernel-commandline-options

   Takes a string argument in the form VARIABLE=VALUE. May be used to set default environment variables to add to forked child processes. May be used more than once to set multiple variables.

.. systemd:option:: systemd.machine_id=
   :group: kernel-commandline-options

   Takes a 32 character hex value to be used for setting the machine-id. Intended mostly for network booting where the same machine-id is desired for every boot.

   .. versionadded:: 229

.. systemd:option:: systemd.set_credential=, systemd.set_credential_binary=
   :group: kernel-commandline-options

   Sets a system credential, which can then be propagated to system services using the :systemd:var:`ImportCredential=` or :systemd:var:`LoadCredential=` setting, see :ref:`systemd.exec(5)` for details. Takes a pair of credential name and value, separated by a colon. The :systemd:var:`systemd.set_credential=` parameter expects the credential value in literal text form, the :systemd:var:`systemd.set_credential_binary=` parameter takes binary data encoded in Base64. Note that the kernel command line is typically accessible by unprivileged programs in :code:`/proc/cmdline`. Thus, this mechanism is not suitable for transferring sensitive data. Use it only for data that is not sensitive (e.g. public keys/certificates, rather than private keys), or in testing/debugging environments.

   For further information see `System and Service Credentials <https://systemd.io/CREDENTIALS>`_ documentation.

   .. versionadded:: 251

.. systemd:option:: systemd.import_credentials=
   :group: kernel-commandline-options

   Takes a boolean argument. If false disables importing credentials from the kernel command line, the DMI/SMBIOS OEM string table, the qemu_fw_cfg subsystem or the EFI kernel stub.

   .. versionadded:: 251

.. systemd:option:: quiet
   :group: kernel-commandline-options

   Turn off status output at boot, much like :systemd:var:`systemd.show_status=no` would. Note that this option is also read by the kernel itself and disables kernel log output. Passing this option hence turns off the usual output from both the system manager and the kernel.

   .. versionadded:: 186

.. systemd:option:: debug
   :group: kernel-commandline-options

   Turn on debugging output. This is equivalent to :systemd:var:`systemd.log_level=debug`. Note that this option is also read by the kernel itself and enables kernel debug output. Passing this option hence turns on the debug output from both the system manager and the kernel.

   .. versionadded:: 205

.. systemd:option:: emergency, rd.emergency, -b
   :group: kernel-commandline-options

   Boot into emergency mode. This is equivalent to :systemd:var:`systemd.unit=emergency.target` or :systemd:var:`rd.systemd.unit=emergency.target`, respectively, and provided for compatibility reasons and to be easier to type.

   .. versionadded:: 186

.. systemd:option:: rescue, rd.rescue, single, s, 1
   :group: kernel-commandline-options

.. systemd:constant:: S
   :group: kernel-commandline-options

   Boot into rescue mode. This is equivalent to :systemd:var:`systemd.unit=rescue.target` or :systemd:var:`rd.systemd.unit=rescue.target`, respectively, and provided for compatibility reasons and to be easier to type.

   .. versionadded:: 186

.. systemd:option:: 2, 3, 4, 5
   :group: kernel-commandline-options

   Boot into the specified legacy SysV runlevel. :systemd:var:`2`, :systemd:var:`3`, and :systemd:var:`4` are equivalent to :systemd:var:`systemd.unit=multi-user.target`; and :systemd:var:`5` is equivalent to :systemd:var:`systemd.unit=graphical.target`, and provided for compatibility reasons and to be easier to type.

   .. versionadded:: 186

.. systemd:option:: locale.LANG=, locale.LANGUAGE=, locale.LC_CTYPE=, locale.LC_NUMERIC=, locale.LC_TIME=, locale.LC_COLLATE=, locale.LC_MONETARY=, locale.LC_MESSAGES=, locale.LC_PAPER=, locale.LC_NAME=, locale.LC_ADDRESS=, locale.LC_TELEPHONE=, locale.LC_MEASUREMENT=, locale.LC_IDENTIFICATION=
   :group: kernel-commandline-options

   Set the system locale to use. This overrides the settings in :code:`/etc/locale.conf`. For more information, see :man-pages:`locale.conf(5)` and :man-pages:`locale(7)`.

   .. versionadded:: 186

For other kernel command line parameters understood by components of the core OS, please refer to :man-pages:`kernel-command-line(7)`.

System Credentials
##################

During initialization the service manager will import credentials from various sources into the system's set of credentials, which can then be propagated into services and consumed by generators:

*    When the service manager first initializes it will read system credentials from SMBIOS Type 11 vendor strings :code:`io.systemd.credential::emphasis:`name`\=:emphasis:`value``, and :code:`io.systemd.credential.binary::emphasis:`name`\=:emphasis:`value``.

*    At the same time it will import credentials from QEMU "fw_cfg". (Note that the SMBIOS mechanism is generally preferred, because it is faster and generic.)

*    Credentials may be passed via the kernel command line, using the :code:`systemd.set-credential=` parameter, see above.

*    Credentials may be passed from the UEFI environment via :ref:`systemd-stub(7)`.

*    When the service manager is invoked during the initrd → host transition it will import all files in :code:`/run/credentials/@initrd/` as system credentials.

Invoke :ref:`systemd-creds(1)` as follows to see the list of credentials passed into the system:

.. code-block:: sh

   # systemd-creds --system list

For further information see `System and Service Credentials <https://systemd.io/CREDENTIALS>`_ documentation.

The service manager when run as PID 1 consumes the following system credentials:

.. systemd:option:: vmm.notify_socket
   :group: system-credentials

   Contains a :systemd:constant:`AF_VSOCK` or :systemd:constant:`AF_UNIX` address where to send a :systemd:constant:`READY=1` notification message when the service manager has completed booting. See :ref:`sd_notify(3)` and the next section for more information. Note that in case the hypervisor does not support :systemd:constant:`SOCK_DGRAM` over :systemd:constant:`AF_VSOCK`, :systemd:constant:`SOCK_SEQPACKET` will be tried instead. The credential payload for :systemd:constant:`AF_VSOCK` should be a string in the form "vsock:CID:PORT". "vsock-stream", "vsock-dgram" and "vsock-seqpacket" can be used instead of "vsock" to force usage of the corresponding socket type.

   This feature is useful for machine managers or other processes on the host to receive a notification via VSOCK when a virtual machine has finished booting.

   .. versionadded:: 254

.. systemd:option:: system.machine_id
   :group: system-credentials

   Takes a 128bit hexadecimal ID to initialize :code:`/etc/machine-id` from, if the file is not set up yet. See :man-pages:`machine-id(5)` for details.

   .. versionadded:: 254

For a list of system credentials various other components of systemd consume, see :ref:`systemd.system-credentials(7)`.

Readiness Protocol
##################

The service manager implements a readiness notification protocol both between the manager and its services (i.e. down the stack), and between the manager and a potential supervisor further up the stack (the latter could be a machine or container manager, or in case of a per-user service manager the system service manager instance). The basic protocol (and the suggested API for it) is described in :ref:`sd_notify(3)`.

The notification socket the service manager (including PID 1) uses for reporting readiness to its own supervisor is set via the usual :code:`$NOTIFY_SOCKET` environment variable (see above). Since this is directly settable only for container managers and for the per-user instance of the service manager, an additional mechanism to configure this is available, in particular intended for use in VM environments: the :code:`vmm.notify_socket` system credential (see above) may be set to a suitable socket (typically an :code:`AF_VSOCK` one) via SMBIOS Type 11 vendor strings. For details see above.

The notification protocol from the service manager up the stack towards a supervisor supports a number of extension fields that allow a supervisor to learn about specific properties of the system and track its boot progress. Specifically the following fields are sent:

*    An :code:`X_SYSTEMD_HOSTNAME=…` message will be sent out once the initial hostname for the system has been determined. Note that during later runtime the hostname might be changed again programmatically, and (currently) no further notifications are sent out in that case.

   .. versionadded:: 256

*    An :code:`X_SYSTEMD_MACHINE_ID=…` message will be sent out once the machine ID of the system has been determined. See :man-pages:`machine-id(5)` for details.

   .. versionadded:: 256

*    An :code:`X_SYSTEMD_SIGNALS_LEVEL=…` message will be sent out once the service manager installed the various UNIX process signal handlers described above. The field's value is an unsigned integer formatted as decimal string, and indicates the supported UNIX process signal feature level of the service manager. Currently, only a single feature level is defined:

   *       :code:`X_SYSTEMD_SIGNALS_LEVEL=2` covers the various UNIX process signals documented above – which are a superset of those supported by the historical SysV init system.

   Signals sent to PID 1 before this message is sent might not be handled correctly yet. A consumer of these messages should parse the value as an unsigned integer that indicates the level of support. For now only the mentioned level 2 is defined, but later on additional levels might be defined with higher integers, that will implement a superset of the currently defined behaviour.

   .. versionadded:: 256

*    :code:`X_SYSTEMD_UNIT_ACTIVE=…` and :code:`X_SYSTEMD_UNIT_INACTIVE=…` messages will be sent out for each target unit as it becomes active or stops being active. This is useful to track boot progress and functionality. For example, once the :code:`ssh-access.target` unit is reported started SSH access is typically available, see :ref:`systemd.special(7)` for details.

   .. versionadded:: 256

*    An :code:`X_SYSTEMD_SHUTDOWN=…` message will be sent out very shortly before the system shuts down. The value is one of the strings "reboot", "halt", "poweroff", "kexec" and indicates which kind of shutdown is being executed.

   .. versionadded:: 256

*    An :code:`X_SYSTEMD_REBOOT_PARAMETER=…` message will also be sent out very shortly before the system shuts down. Its value is the reboot argument as configured with :code:`systemctl --reboot-argument=…`.

   .. versionadded:: 256

Note that these extension fields are sent in addition to the regular "READY=1" and "RELOADING=1" notifications.

Options
#######

:code:`systemd` is only very rarely invoked directly, since it is started early and is already running by the time users may interact with it. Normally, tools like :man-pages:`systemctl(1)` are used to give commands to the manager. Since :code:`systemd` is usually not invoked directly, the options listed below are mostly useful for debugging and special purposes.

Introspection and debugging options
###################################

Those options are used for testing and introspection, and :code:`systemd` may be invoked with them at any time:

.. systemd:option:: --dump-configuration-items

   Dump understood unit configuration items. This outputs a terse but complete list of configuration items understood in unit definition files.

.. systemd:option:: --dump-bus-properties

   Dump exposed bus properties. This outputs a terse but complete list of properties exposed on D-Bus.

   .. versionadded:: 239

.. systemd:option:: --test

   Determine the initial start-up transaction (i.e. the list of jobs enqueued at start-up), dump it and exit — without actually executing any of the determined jobs. This option is useful for debugging only. Note that during regular service manager start-up additional units not shown by this operation may be started, because hardware, socket, bus or other kinds of activation might add additional jobs as the transaction is executed. Use :code:`--system` to request the initial transaction of the system service manager (this is also the implied default), combine with :code:`--user` to request the initial transaction of the per-user service manager instead.

.. systemd:option:: --system, --user

   When used in conjunction with :code:`--test`, selects whether to calculate the initial transaction for the system instance or for a per-user instance. These options have no effect when invoked without :code:`--test`, as during regular (i.e. non-:code:`--test`) invocations the service manager will automatically detect whether it shall operate in system or per-user mode, by checking whether the PID it is run as is 1 or not. Note that it is not supported booting and maintaining a system with the service manager running in :code:`--system` mode but with a PID other than 1.

System clock epoch
##################

When :code:`systemd` is started or restarted, it may set the system clock to the "epoch". This mechanism is used to ensure that the system clock remains somewhat reasonably initialized and roughly monotonic across reboots, in case no battery-backed local RTC is available or it does not work correctly.

The epoch is the lowest date above which the system clock time is assumed to be set correctly. When initializing, the local clock is *advanced* to the epoch if it was set to a lower value. As a special case, if the local clock is sufficiently far in the future (by default 15 years, but this can be configured at build time), the hardware clock is assumed to be broken, and the system clock is to the epoch if it was set to a lower value. As a special case, if the local clock is sufficiently far in the future (by default 15 years, but this can be configured at build time), the hardware clock is assumed to be broken, and the system clock is *rewound* to the epoch. to the epoch.

The epoch is set to the highest of: the build time of :code:`systemd`, the modification time ("mtime") of :code:`/usr/lib/clock-epoch`, and the modification time of :code:`/var/lib/systemd/timesync/clock`.

Files
#####

.. systemd:option:: /run/systemd/notify

   Daemon status notification socket. This is an :code:`AF_UNIX` datagram socket and is used to implement the daemon notification logic as implemented by :ref:`sd_notify(3)`.

.. systemd:option:: /run/systemd/private

   Used internally as communication channel between :man-pages:`systemctl(1)` and the systemd process. This is an :code:`AF_UNIX` stream socket. This interface is private to systemd and should not be used in external projects.

.. systemd:option:: /usr/lib/clock-epoch

   The modification time ("mtime") of this file is used for the time epoch, see previous section.

.. systemd:option:: /var/lib/systemd/timesync/clock

   The modification time ("mtime") of this file is updated by :ref:`systemd-timesyncd.service(8)`. If present, the modification time of file is used for the epoch, see previous section.
