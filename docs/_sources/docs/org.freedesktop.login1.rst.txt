Name
####

org.freedesktop.login1 — The D-Bus interface of systemd-logind

Introduction
############

:ref:`systemd-logind.service(8)` is a system service that keeps track of user logins and seats.

The daemon provides both a C library interface as well as a D-Bus interface. The library interface may be used to introspect and watch the state of user logins and seats. The bus interface provides the same functionality but in addition may also be used to make changes to the system state. For more information please consult :ref:`sd-login(3)`.

Methods
#######

:code:`GetSession()` may be used to get the session object path for the session with the specified ID. Similarly, :code:`GetUser()` and :code:`GetSeat()` get the user and seat objects, respectively. :code:`GetSessionByPID()` and :code:`GetUserByPID()` get the session/user object the specified PID belongs to if there is any.

:code:`ListSessions()` returns an array of all current sessions. The structures in the array consist of the following fields: :code:`session id`, :code:`user id`, :code:`user name`, :code:`seat id`, and :code:`session object path`. If a session does not have a seat attached, the seat id field will be an empty string.

:code:`ListSessionsEx()` returns an array of all current sessions with more metadata than :code:`ListSessions()`. The structures in the array consist of the following fields: :code:`session id`, :code:`user id`, :code:`user name`, :code:`seat id`, :code:`leader pid`, :code:`session class`, :code:`tty name`, :code:`idle hint`, :code:`idle hint monotonic timestamp`, and :code:`session object path`. :code:`tty` and :code:`seat id` fields could be empty, if the session has no associated tty or session has no seat attached, respectively.

:code:`ListUsers()` returns an array of all currently logged in users. The structures in the array consist of the following fields: user id, user name, user object path.

:code:`ListSeats()` returns an array of all currently available seats. The structure in the array consists of the following fields: seat id, seat object path.

:code:`ListInhibitors()` lists all currently active inhibitors. It returns an array of structures consisting of :code:`what`, :code:`who`, :code:`why`, :code:`mode`, :code:`uid` (user ID), and :code:`pid` (process ID).

:code:`CreateSession()`, :code:`CreateSessionWithPIDFD()`, and :code:`ReleaseSession()` may be used to open or close login sessions. These calls should *never* be invoked directly by clients. Creating/closing sessions is exclusively the job of PAM and its be invoked directly by clients. Creating/closing sessions is exclusively the job of PAM and its :man-pages:`pam_systemd(8)` module.

:code:`ActivateSession()` brings the session with the specified ID into the foreground. :code:`ActivateSessionOnSeat()` does the same, but only if the seat id matches.

:code:`LockSession()` asks the session with the specified ID to activate the screen lock. :code:`UnlockSession()` asks the session with the specified ID to remove an active screen lock, if there is any. This is implemented by sending out the Lock() and Unlock() signals from the respective session object which session managers are supposed to listen on.

:code:`LockSessions()` asks all sessions to activate their screen locks. This may be used to lock access to the entire machine in one action. Similarly, :code:`UnlockSessions()` asks all sessions to deactivate their screen locks.

:code:`KillSession()` may be used to send a Unix signal to one or all processes of a session. As arguments it takes the session id, either the string "leader" or "all" and a signal number. If "leader" is passed only the session "leader" is killed. If "all" is passed all processes of the session are killed.

:code:`KillUser()` may be used to send a Unix signal to all processes of a user. As arguments it takes the user id and a signal number.

:code:`TerminateSession()`, :code:`TerminateUser()`, :code:`TerminateSeat()` may be used to forcibly terminate one specific session, all processes of a user, and all sessions attached to a specific seat, respectively. The session, user, and seat are identified by their respective IDs.

:code:`SetUserLinger()` enables or disables user lingering. If enabled, the runtime directory of a user is kept around and they may continue to run processes while logged out. If disabled, the runtime directory goes away as soon as they log out. :code:`SetUserLinger()` expects three arguments: the UID, a boolean whether to enable/disable and a boolean controlling the `polkit <https://www.freedesktop.org/software/polkit/docs/latest/>`_ authorization interactivity (see below). Note that the user linger state is persistently stored on disk.

:code:`AttachDevice()` may be used to assign a specific device to a specific seat. The device is identified by its :code:`/sys/` path and must be eligible for seat assignments. :code:`AttachDevice()` takes three arguments: the seat id, the sysfs path, and a boolean for controlling polkit interactivity (see below). Device assignments are persistently stored on disk. To create a new seat, simply specify a previously unused seat id. For more information about the seat assignment logic see :ref:`sd-login(3)`.

:code:`FlushDevices()` removes all explicit seat assignments for devices, resetting all assignments to the automatic defaults. The only argument it takes is the polkit interactivity boolean (see below).

:code:`PowerOff()`, :code:`Reboot()`, :code:`Halt()`, :code:`Suspend()`, and :code:`Hibernate()` result in the system being powered off, rebooted, halted (shut down without turning off power), suspended (the system state is saved to RAM and the CPU is turned off), or hibernated (the system state is saved to disk and the machine is powered down). :code:`HybridSleep()` results in the system entering a hybrid-sleep mode, i.e. the system is both hibernated and suspended. :code:`SuspendThenHibernate()` results in the system being suspended, then later woken using an RTC timer and hibernated. The only argument is the polkit interactivity boolean :code:`interactive` (see below). The main purpose of these calls is that they enforce polkit policy and hence allow powering off/rebooting/suspending/hibernating even by unprivileged users. They also enforce inhibition locks for non-privileged users. :code:`Sleep()` automatically selects the most suitable sleep operation supported by the machine. The candidate sleep operations to check for support can be configured through :code:`SleepOperation=` setting in :man-pages:`logind.conf(5)`. UIs should expose these calls as the primary mechanism to poweroff/reboot/suspend/hibernate the machine. Methods :code:`PowerOffWithFlags()`, :code:`RebootWithFlags()`, :code:`HaltWithFlags()`, :code:`SuspendWithFlags()`, :code:`HibernateWithFlags()`, :code:`HybridSleepWithFlags()`, :code:`SuspendThenHibernateWithFlags()`, and :code:`Sleep()` take :code:`flags` to allow for extendability, defined as follows:

.. code-block:: sh

   #define SD_LOGIND_ROOT_CHECK_INHIBITORS          (UINT64_C(1) << 0)
   #define SD_LOGIND_KEXEC_REBOOT                   (UINT64_C(1) << 1)
   #define SD_LOGIND_SOFT_REBOOT                    (UINT64_C(1) << 2)
   #define SD_LOGIND_SOFT_REBOOT_IF_NEXTROOT_SET_UP (UINT64_C(1) << 3)
   #define SD_LOGIND_SKIP_INHIBITORS                (UINT64_C(1) << 4)

When the :code:`flags` is 0 then these methods behave just like the versions without flags. Since systemd version 257 inhibitors of type "block" are enforced on operations requested by both privileged and unprivileged users. Previously they were honoured only by unprivileged users, excluding the user owning the inhibitor. The latter behaviour is now available through the "block-weak" inhibitor lock type. :code:`SD_LOGIND_ROOT_CHECK_INHIBITORS` (0x01) makes "block-weak" locks behave like regular "block" locks, i.e. ensures they are honoured for any user. A flag :code:`SD_LOGIND_SKIP_INHIBITORS` (0x10) can be specified to bypass both "block" and "block-weak" inhibitors (it has no effect on "delay" inhibitors). When :code:`SD_LOGIND_KEXEC_REBOOT` (0x02) is set, then :code:`RebootWithFlags()` performs a kexec reboot if kexec kernel is loaded. When :code:`SD_LOGIND_SOFT_REBOOT` (0x04) is set, or :code:`SD_LOGIND_SOFT_REBOOT_IF_NEXTROOT_SET_UP` (0x08) is set and a new root file system has been set up on "/run/nextroot/", then :code:`RebootWithFlags()` performs a userspace reboot only. :code:`SD_LOGIND_SOFT_REBOOT_IF_NEXTROOT_SET_UP` and :code:`SD_LOGIND_KEXEC_REBOOT` can be combined, with soft-reboot having precedence.

:code:`SetRebootParameter()` sets a parameter for a subsequent reboot operation. See the description of :code:`reboot` in :man-pages:`systemctl(1)` and :man-pages:`reboot(2)` for more information.

:code:`SetRebootToFirmwareSetup()`, :code:`SetRebootToBootLoaderMenu()`, and :code:`SetRebootToBootLoaderEntry()` configure the action to be taken from the boot loader after a reboot: respectively entering firmware setup mode, the boot loader menu, or a specific boot loader entry. See :man-pages:`systemctl(1)` for the corresponding command line interface.

:code:`CanPowerOff()`, :code:`CanReboot()`, :code:`CanHalt()`, :code:`CanSuspend()`, :code:`CanHibernate()`, :code:`CanHybridSleep()`, :code:`CanSuspendThenHibernate()`, :code:`CanSleep()`, :code:`CanRebootParameter()`, :code:`CanRebootToFirmwareSetup()`, :code:`CanRebootToBootLoaderMenu()`, and :code:`CanRebootToBootLoaderEntry()` test whether the system supports the respective operation and whether the calling user is allowed to execute it. Returns one of "na", "yes", "no", and "challenge". If "na" is returned, the operation is not available because hardware, kernel, or drivers do not support it. If "yes" is returned, the operation is supported and the user may execute the operation without further authentication. If "no" is returned, the operation is available but the user is not allowed to execute the operation. If "challenge" is returned, the operation is available but only after authorization.

:code:`ScheduleShutdown()` schedules a shutdown operation :code:`type` at time :code:`usec` in microseconds since the UNIX epoch. Alternatively, if :code:`usec` "UINT64_MAX" and a maintenance window is configured, :code:`systemd-logind` will use the next time of the maintenance window instead. :code:`type` can be one of "poweroff", "dry-poweroff", "reboot", "dry-reboot", "halt", and "dry-halt". (The "dry-" variants do not actually execute the shutdown action.) :code:`CancelScheduledShutdown()` cancels a scheduled shutdown. The output parameter :code:`cancelled` is true if a shutdown operation was scheduled.

:code:`SetWallMessage()` sets the wall message (the message that will be sent out to all terminals and stored in a :man-pages:`utmp(5)` record) for a subsequent scheduled shutdown operation. The parameter :code:`wall_message` specifies the shutdown reason (and may be empty) which will be included in the shutdown message. The parameter :code:`enable` specifies whether to print a wall message on shutdown.

:code:`Inhibit()` creates an inhibition lock. It takes four parameters: :code:`what`, :code:`who`, :code:`why`, and :code:`mode`. :code:`what` is one or more of "shutdown", "sleep", "idle", "handle-power-key", "handle-suspend-key", "handle-hibernate-key", "handle-lid-switch", separated by colons, for inhibiting poweroff/reboot, suspend/hibernate, the automatic idle logic, or hardware key handling. :code:`who` should be a short human-readable string identifying the application taking the lock. :code:`why` should be a short human-readable string identifying the reason why the lock is taken. Finally, :code:`mode` is either "block" or "delay" which encodes whether the inhibit shall be consider mandatory or whether it should just delay the operation to a certain maximum time, while the "block-weak" and variants will create an inhibitor that is automatically ignored in some circumstances. The method returns a file descriptor. The lock is released the moment this file descriptor and all its duplicates are closed. For more information on the inhibition logic see `Inhibitor Locks <https://systemd.io/INHIBITOR_LOCKS>`_.

Signals
#######

Whenever the inhibition state or idle hint changes, :code:`PropertyChanged` signals are sent out to clients which have subscribed.

The :code:`SecureAttentionKey()` signal is sent when the user presses Ctrl+Alt+Shift+Esc to request the login manager to display the greeter, for instance in the case of a deadlocked compositor.

The :code:`SessionNew()`, :code:`SessionRemoved()`, :code:`UserNew()`, :code:`UserRemoved()`, :code:`SeatNew()`, and :code:`SeatRemoved()` signals are sent each time a session is created or removed, a user logs in or out, or a seat is added or removed. They each contain the ID of the object plus the object path.

The :code:`PrepareForShutdown()`, :code:`PrepareForShutdownWithMetadata()`, and :code:`PrepareForSleep()` signals are sent right before (with the argument "true") or after (with the argument "false") the system goes down for reboot/poweroff and suspend/hibernate, respectively. This may be used by applications to save data on disk, release memory, or do other jobs that should be done shortly before shutdown/sleep, in conjunction with delay inhibitor locks. After completion of this work they should release their inhibition locks in order to not delay the operation any further. For more information see `Inhibitor Locks <https://systemd.io/INHIBITOR_LOCKS>`_. The :code:`PrepareForShutdownWithMetadata()` signal additionally sends a list of key/value pair metadata fields. Currently it sends a :code:`type` string which defines the type of shutdown. The type can be one of "power-off", "reboot", "halt", "kexec" or "soft-reboot". This signal is sent first, followed by :code:`PrepareForShutdown()` (for backward compatibility).

Properties
##########

Most properties simply reflect the configuration, see :man-pages:`logind.conf(5)`. This includes: :code:`NAutoVTs`, :code:`KillOnlyUsers`, :code:`KillExcludeUsers`, :code:`KillUserProcesses`, :code:`IdleAction`, :code:`InhibitDelayMaxUSec`, :code:`InhibitorsMax`, :code:`UserStopDelayUSec`, :code:`HandlePowerKey`, :code:`HandleSuspendKey`, :code:`HandleHibernateKey`, :code:`HandleLidSwitch`, :code:`HandleLidSwitchExternalPower`, :code:`HandleLidSwitchDocked`, :code:`IdleActionUSec`, :code:`HoldoffTimeoutUSec`, :code:`RemoveIPC`, :code:`RuntimeDirectorySize`, :code:`RuntimeDirectoryInodesMax`, :code:`InhibitorsMax`, and :code:`SessionsMax`.

The :code:`IdleHint` property reflects the idle hint state of the system. If the system is idle it might get into automatic suspend or shutdown depending on the configuration.

:code:`IdleSinceHint` and :code:`IdleSinceHintMonotonic` encode the timestamps of the last change of the idle hint boolean, in :code:`CLOCK_REALTIME` and :code:`CLOCK_MONOTONIC` timestamps, respectively, in microseconds since the epoch.

The :code:`BlockInhibited`, :code:`BlockWeakInhibited`, and :code:`DelayInhibited` properties encode the currently active locks of the respective modes. They are colon separated lists of "shutdown", "sleep", and "idle" (see above).

:code:`NCurrentSessions` and :code:`NCurrentInhibitors` contain the number of currently registered sessions and inhibitors.

The :code:`BootLoaderEntries` property contains a list of boot loader entries. This includes boot loader entries defined in configuration and any additional loader entries reported by the boot loader. See :ref:`systemd-boot(7)` for more information.

The :code:`PreparingForShutdown` and :code:`PreparingForSleep` boolean properties are true during the interval between the two :code:`PrepareForShutdown()` and :code:`PrepareForSleep()` signals respectively. The :code:`PreparingForShutdownWithMetadata` property provides a list of key/value pair metadata fields. Currently it lists a :code:`preparing` boolean that corresponds to the :code:`PreparingForShutdown` property, and, if a shutdown is being prepared, it will also contain a :code:`type` string which defines the type of shutdown. The type can be one of "power-off", "reboot", "halt", "kexec" or "soft-reboot". Note that these properties do not send out :code:`PropertyChanged` signals.

The :code:`RebootParameter` property shows the value set with the :code:`SetRebootParameter()` method described above.

:code:`ScheduledShutdown` shows the value pair set with the :code:`ScheduleShutdown()` method described above.

:code:`RebootToFirmwareSetup`, :code:`RebootToBootLoaderMenu`, and :code:`RebootToBootLoaderEntry` are true when the resprective post-reboot operation was selected with :code:`SetRebootToFirmwareSetup()`, :code:`SetRebootToBootLoaderMenu()`, or :code:`SetRebootToBootLoaderEntry()`.

The :code:`WallMessage` and :code:`EnableWallMessages` properties reflect the shutdown reason and wall message enablement switch which can be set with the :code:`SetWallMessage()` method described above.

:code:`Docked` is true if the machine is connected to a dock. :code:`LidClosed` is true when the lid (of a laptop) is closed. :code:`OnExternalPower` is true when the machine is connected to an external power supply.

Security
########

A number of operations are protected via the polkit privilege system. :code:`SetUserLinger()` requires the :code:`org.freedesktop.login1.set-user-linger` privilege. :code:`AttachDevice()` requires :code:`org.freedesktop.login1.attach-device` and :code:`FlushDevices()` requires :code:`org.freedesktop.login1.flush-devices`. :code:`PowerOff()`, :code:`Reboot()`, :code:`Halt()`, :code:`Suspend()`, :code:`Hibernate()` require :code:`org.freedesktop.login1.power-off`, :code:`org.freedesktop.login1.power-off-multiple-sessions`, :code:`org.freedesktop.login1.power-off-ignore-inhibit`, :code:`org.freedesktop.login1.reboot`, :code:`org.freedesktop.login1.reboot-multiple-sessions`, :code:`org.freedesktop.login1.reboot-ignore-inhibit`, :code:`org.freedesktop.login1.halt`, :code:`org.freedesktop.login1.halt-multiple-sessions`, :code:`org.freedesktop.login1.halt-ignore-inhibit`, :code:`org.freedesktop.login1.suspend`, :code:`org.freedesktop.login1.suspend-multiple-sessions`, :code:`org.freedesktop.login1.suspend-ignore-inhibit`, :code:`org.freedesktop.login1.hibernate`, :code:`org.freedesktop.login1.hibernate-multiple-sessions`, :code:`org.freedesktop.login1.hibernate-ignore-inhibit`, respectively depending on whether there are other sessions around or active inhibits are present. :code:`HybridSleep()` and :code:`SuspendThenHibernate()` use the same privileges as :code:`Hibernate()`. :code:`Sleep()` uses the inhibits of the auto-selected sleep operation. :code:`SetRebootParameter()` requires :code:`org.freedesktop.login1.set-reboot-parameter`.

:code:`SetRebootToFirmwareSetup()` requires :code:`org.freedesktop.login1.set-reboot-to-firmware-setup`. :code:`SetRebootToBootLoaderMenu()` requires :code:`org.freedesktop.login1.set-reboot-to-boot-loader-menu`. :code:`SetRebootToBootLoaderEntry()` requires :code:`org.freedesktop.login1.set-reboot-to-boot-loader-entry`.

:code:`ScheduleShutdown()` and :code:`CancelScheduledShutdown()` require the same privileges (listed above) as the immediate poweroff/reboot/halt operations.

:code:`Inhibit()` is protected via one of :code:`org.freedesktop.login1.inhibit-block-shutdown`, :code:`org.freedesktop.login1.inhibit-delay-shutdown`, :code:`org.freedesktop.login1.inhibit-block-sleep`, :code:`org.freedesktop.login1.inhibit-delay-sleep`, :code:`org.freedesktop.login1.inhibit-block-idle`, :code:`org.freedesktop.login1.inhibit-handle-power-key`, :code:`org.freedesktop.login1.inhibit-handle-suspend-key`, :code:`org.freedesktop.login1.inhibit-handle-hibernate-key`, :code:`org.freedesktop.login1.inhibit-handle-lid-switch` depending on the lock type and mode taken.

The :code:`interactive` boolean parameters can be used to control whether polkit should interactively ask the user for authentication credentials if required.

Methods
#######

:code:`Terminate()`, :code:`Activate()`, :code:`Lock()`, :code:`Unlock()`, and :code:`Kill()` work similarly to the respective calls on the :code:`Manager` object.

:code:`SetIdleHint()` is called by the session object to update the idle state of the session whenever it changes.

:code:`TakeControl()` allows a process to take exclusive managed device access-control for that session. Only one D-Bus connection can be a controller for a given session at any time. If the :code:`force` argument is set (root only), an existing controller is kicked out and replaced. Otherwise, this method fails if there is already a controller. Note that this method is limited to D-Bus users with the effective UID set to the user of the session or root.

:code:`ReleaseControl()` drops control of a given session. Closing the D-Bus connection implicitly releases control as well. See :code:`TakeControl()` for more information. This method also releases all devices for which the controller requested ownership via :code:`TakeDevice()`.

:code:`SetType()` allows the type of the session to be changed dynamically. It can only be called by session's current controller. If :code:`TakeControl()` has not been called, this method will fail. In addition, the session type will be reset to its original value once control is released, either by calling :code:`ReleaseControl()` or closing the D-Bus connection. This should help prevent a session from entering an inconsistent state, for example if the controller crashes. The only argument :code:`type` is the new session type.

:code:`SetClass()` allows the caller to change the class of the session dynamically. It may only be called by session's owning user. Currently, this call may be exclusively used to change the class from "user-incomplete" to "user". The call is synchronous, and will return only once the user's service manager has successfully been started, if necessary. The only argument :code:`type` is the new session type.

:code:`SetDisplay()` allows the display name of the graphical session to be changed. This is useful if the display server is started as part of the session. It can only be called by session's current controller. If :code:`TakeControl()` has not been called, this method will fail. The only argument :code:`display` is the new display name.

:code:`SetTTY()` allows the device name of the session to be changed. This is useful if the tty device is only known after authentication. It can only be called by session's current controller. If :code:`TakeControl()` has not been called, this method will fail. The only argument :code:`tty_fd` is a file handle to the new tty device.

:code:`TakeDevice()` allows a session controller to get a file descriptor for a specific device. Pass in the major and minor numbers of the character device and :code:`systemd-logind` will return a file descriptor for the device. Only a limited set of device-types is currently supported (but may be extended). :code:`systemd-logind` automatically mutes the file descriptor if the session is inactive and resumes it once the session is activated again. This guarantees that a session can only access session devices if the session is active. Note that this revoke/resume mechanism is asynchronous and may happen at any given time. This only works on devices that are attached to the seat of the given session. A process is not required to have direct access to the device node. :code:`systemd-logind` only requires you to be the active session controller (see :code:`TakeControl()`). Also note that any device can only be requested once. As long as you do not release it, further :code:`TakeDevice()` calls will fail.

:code:`ReleaseDevice()` releases a device again (see :code:`TakeDevice()`). This is also implicitly done by :code:`ReleaseControl()` or when closing the D-Bus connection.

:code:`PauseDeviceComplete()` allows a session controller to synchronously pause a device after receiving a :code:`PauseDevice("pause")` signal. Forced signals (or after an internal timeout) are automatically completed by :code:`systemd-logind` asynchronously.

:code:`SetLockedHint()` may be used to set the "locked hint" to :code:`locked`, i.e. information whether the session is locked. This is intended to be used by the desktop environment to tell :code:`systemd-logind` when the session is locked and unlocked.

:code:`SetBrightness()` may be used to set the display brightness. This is intended to be used by the desktop environment and allows unprivileged programs to access hardware settings in a controlled way. The :code:`subsystem` parameter specifies a kernel subsystem, either "backlight" or "leds". The :code:`name` parameter specifies a device name under the specified subsystem. The :code:`brightness` parameter specifies the brightness. The range is defined by individual drivers, see :code:`/sys/class/:code:`subsystem`/:code:`name`/max_brightness`.

Signals
#######

The active session controller exclusively gets :code:`PauseDevice()` and :code:`ResumeDevice()` events for any device it requested via :code:`TakeDevice()`. They notify the controller whenever a device is paused or resumed. A device is never resumed if its session is inactive. Also note that :code:`PauseDevice()` signals are sent before the :code:`PropertyChanged` signal for the :code:`Active` state. The inverse is true for :code:`ResumeDevice()`. A device may remain paused for unknown reasons even though the :code:`Session` is active.

A :code:`PauseDevice()` signal carries the major and minor numbers and a string describing the type as arguments. :code:`force` means the device was already paused by :code:`systemd-logind` and the signal is only an asynchronous notification. :code:`pause` means :code:`systemd-logind` grants you a limited amount of time to pause the device. You must respond to this via :code:`PauseDeviceComplete()`. This synchronous pausing mechanism is used for backwards-compatibility to VTs and :code:`systemd-logind` is free to not make use of it. It is also free to send a forced :code:`PauseDevice()` if you do not respond in a timely manner (or for any other reason). :code:`gone` means the device was unplugged from the system and you will no longer get any notifications about it. There is no need to call :code:`ReleaseDevice()`. You may call :code:`TakeDevice()` again if a new device is assigned the major+minor combination.

:code:`ResumeDevice()` is sent whenever a session is active and a device is resumed. It carries the major/minor numbers as arguments and provides a new open file descriptor. You should switch to the new descriptor and close the old one. They are not guaranteed to have the same underlying open file descriptor in the kernel (except for a limited set of device types).

Whenever :code:`Active` or the idle state changes, :code:`PropertyChanged` signals are sent out to clients which have subscribed.

:code:`Lock()`/:code:`Unlock()` is sent when the session is asked to be screen-locked/unlocked. A session manager of the session should listen to this signal and act accordingly. This signal is sent out as a result of the :code:`Lock()` and :code:`Unlock()` methods, respectively.

Signals are only emitted on objects referencing a specific session ID, not on the "/org/freedesktop/login1/session/self" or "/org/freedesktop/login1/session/auto" convenience objects, as they can only be dereferenced relative to a method caller.

Properties
##########

:code:`Id` encodes the session ID.

:code:`User` encodes the user ID of the user this session belongs to. This is a structure consisting of the Unix UID and the object path.

:code:`Name` encodes the user name.

:code:`Timestamp` and :code:`TimestampMonotonic` encode the microseconds since the epoch when the session was created, in :code:`CLOCK_REALTIME` or :code:`CLOCK_MONOTONIC`, respectively.

:code:`VTNr` encodes the virtual terminal number of the session if there is any, 0 otherwise.

:code:`Seat` encodes the seat this session belongs to if there is any. This is a structure consisting of the ID and the seat object path.

:code:`TTY` encodes the kernel TTY path of the session if this is a text login. If not this is an empty string.

:code:`Display` encodes the X11 display name if this is a graphical login. If not, this is an empty string.

:code:`Remote` encodes whether the session is local or remote.

:code:`RemoteHost` and :code:`RemoteUser` encode the remote host and user if this is a remote session, or an empty string otherwise.

:code:`Service` encodes the PAM service name that registered the session.

:code:`Desktop` describes the desktop environment running in the session (if known).

:code:`Scope` contains the systemd scope unit name of this session.

:code:`Leader` encodes the PID of the process that registered the session.

:code:`LeaderPIDFDId` encodes the Linux pidfd inode ID of the process that registered the session.

:code:`Audit` encodes the Kernel Audit session ID of the session if auditing is available.

:code:`Type` encodes the session type. It's one of "unspecified" (for cron PAM sessions and suchlike), "tty" (for text logins), "web" (for web-based logins), or "x11"/"mir"/"wayland" (for graphical logins).

:code:`Class` encodes the session class. It's one of "user" (for normal user sessions), "greeter" (for display manager pseudo-sessions), or "lock-screen" (for display lock screens).

:code:`Active` is a boolean that is true if the session is active, i.e. currently in the foreground. This field is semi-redundant due to :code:`State`.

:code:`State` encodes the session state and one of "online", "active", or "closing". See :ref:`sd_session_get_state(3)` for more information about the states.

:code:`IdleHint`, :code:`IdleSinceHint`, and :code:`IdleSinceHintMonotonic` encapsulate the idle hint state of this session, similarly to how the respective properties on the manager object do it for the whole system.

:code:`LockedHint` shows the locked hint state of this session, as set by the :code:`SetLockedHint()` method described above.

:code:`CanIdle` indicates whether the session supports the idle hint concept. Similarly, :code:`CanLock` indicates whether the session supports the screen lock concept.
