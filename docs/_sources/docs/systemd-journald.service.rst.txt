Description
###########

:code:`systemd-journald` is a system service that collects and stores logging data. It creates and maintains structured, indexed journals based on logging information that is received from a variety of sources:

*    Kernel log messages, via kmsg

*    Simple system log messages, via the :code:`libc` :man-pages:`syslog(3)` call

*    Structured system log messages via the native Journal API, see :ref:`sd_journal_print(3)` and `Native Journal Protocol <https://systemd.io/JOURNAL_NATIVE_PROTOCOL>`_

*    Standard output and standard error of service units. For further details see below.

*    Audit records, originating from the kernel audit subsystem

The daemon will implicitly collect numerous metadata fields for each log messages in a secure and unfakeable way. See :ref:`systemd.journal-fields(7)` for more information about the collected metadata.

Log data collected by the journal is primarily text-based but can also include binary data where necessary. Individual fields making up a log record stored in the journal may be up to 2⁶⁴-1 bytes in size.

The journal service stores log data either persistently below :code:`/var/log/journal` or in a volatile way below :code:`/run/log/journal/` (in the latter case, it is lost at reboot). By default, log data is stored persistently if :code:`/var/log/journal/` exists during boot, with an implicit fallback to volatile storage otherwise. Use :code:`Storage=` in :man-pages:`journald.conf(5)` to configure where log data is placed, independently of the existence of :code:`/var/log/journal/`.

Note that journald will initially use volatile storage, until a call to :code:`journalctl --flush` (or sending :code:`SIGUSR1` to journald) will cause it to switch to persistent logging (under the conditions mentioned above). This is done automatically on boot via "systemd-journal-flush.service".

On systems where :code:`/var/log/journal/` does not exist yet but where persistent logging is desired (and the default :code:`journald.conf` is used), it is sufficient to create the directory, and ensure it has the correct access modes and ownership:

.. code-block:: sh

   mkdir -p /var/log/journal
   systemd-tmpfiles --create --prefix /var/log/journal

See :man-pages:`journald.conf(5)` for information about the configuration of this service.

Stream logging
##############

The systemd service manager invokes all service processes with standard output and standard error connected to the journal by default. This behaviour may be altered via the :code:`StandardOutput=`/:code:`StandardError=` unit file settings, see :ref:`systemd.exec(5)` for details. The journal converts the log byte stream received this way into individual log records, splitting the stream at newline ("\\n", ASCII :code:`10`) and :code:`NUL` bytes.

If :code:`systemd-journald.service` is stopped, the stream connections associated with all services are terminated. Further writes to those streams by the service will result in :code:`EPIPE` errors. In order to react gracefully in this case, it is recommended that programs logging to standard output/error ignore such errors. If the :code:`SIGPIPE` UNIX signal handler is not blocked or turned off, such write attempts will also result in such process signals being generated, see :man-pages:`signal(7)`. To mitigate this issue, systemd service manager explicitly turns off the :code:`SIGPIPE` signal for all invoked processes by default (this may be changed for each unit individually via the :code:`IgnoreSIGPIPE=` option, see :ref:`systemd.exec(5)` for details). After the standard output/standard error streams have been terminated they may not be recovered until the services they are associated with are restarted. Note that during normal operation, :code:`systemd-journald.service` stores copies of the file descriptors for those streams in the service manager. If :code:`systemd-journald.service` is restarted using :code:`systemctl restart` or equivalent operation instead of a pair of separate :code:`systemctl stop` and :code:`systemctl start` commands (or equivalent operations), these stream connections are not terminated and survive the restart. It is thus safe to restart :code:`systemd-journald.service`, but stopping it is not recommended.

Note that the log record metadata for records transferred via such standard output/error streams reflect the metadata of the peer the stream was originally created for. If the stream connection is passed on to other processes (such as further child processes forked off the main service process), the log records will not reflect their metadata, but will continue to describe the original process. This is different from the other logging transports listed above, which are inherently record based and where the metadata is always associated with the individual record.

In addition to the implicit standard output/error logging of services, stream logging is also available via the :ref:`systemd-cat(1)` command line tool.

Currently, the number of parallel log streams :code:`systemd-journald` will accept is limited to 4096. When this limit is reached further log streams may be established but will receive :code:`EPIPE` right from the beginning.

Journal Namespaces
##################

Journal 'namespaces' are both a mechanism for logically isolating the log stream of projects consisting of one or more services from the rest of the system and a mechanism for improving performance. Multiple journal namespaces may exist simultaneously, each defining its own, independent log stream managed by its own instance of :code:`systemd-journald`. Namespaces are independent of each other, both in the data store and in the IPC interface. By default, only a single "default namespace exists, managed by :code:`systemd-journald.service` (and its associated socket units). Additional namespaces are created by starting an instance of the :code:`systemd-journald@.service` service template. The instance name is the namespace identifier, which is a short string used for referencing the journal namespace. Service units may be assigned to a specific journal namespace through the :code:`LogNamespace=` unit file setting, see :ref:`systemd.exec(5)` for details. The :code:`--namespace=` switch of :man-pages:`journalctl(1)` may be used to view the log stream of a specific namespace. If the switch is not used the log stream of the default namespace is shown, i.e. log data from other namespaces is not visible.

Services associated with a specific log namespace may log via :man-pages:`syslog(3)`, the native logging protocol of the journal and via stdout/stderr; the logging from all three transports is associated with the namespace.

By default, only the default namespace will collect kernel and audit log messages.

The :code:`systemd-journald` instance of the default namespace is configured through :code:`/etc/systemd/journald.conf` (see below), while the other instances are configured through :code:`/etc/systemd/journald@NAMESPACE.conf`. The journal log data for the default namespace is placed in :code:`/var/log/journal/MACHINE_ID` (see below) while the data for the other namespaces is located in :code:`/var/log/journal/MACHINE_ID.NAMESPACE`.

Signals
#######

.. systemd:constant:: SIGUSR1

   Request that journal data from :code:`/run/` is flushed to :code:`/var/` in order to make it persistent (if this is enabled). This must be used after :code:`/var/` is mounted, as otherwise log data from :code:`/run/` is never flushed to :code:`/var/` regardless of the configuration. Use the :code:`journalctl --flush` command to request flushing of the journal files, and wait for the operation to complete. See :man-pages:`journalctl(1)` for details.

   .. versionadded:: 186

.. systemd:constant:: SIGUSR2

   Request immediate rotation of the journal files. Use the :code:`journalctl --rotate` command to request journal file rotation, and wait for the operation to complete.

   .. versionadded:: 186

.. systemd:constant:: SIGRTMIN+1

   Request that all unwritten log data is written to disk. Use the :code:`journalctl --sync` command to trigger journal synchronization, and wait for the operation to complete.

   .. versionadded:: 228

.. systemd:constant:: SIGHUP

   Upon reception of the :code:`SIGHUP` process signal :code:`systemd-journald` will reload its configuration values and update the kernel log buffer and journals to reflect the new configuration. If :code:`ReadKmsg=` has changed, the kernel log buffer will be flushed and updated as part of the reload. The active journal (e.g., persistent, volatile) will continue to be used with the updated configuration. However, if the storage mode has changed from persistent to volatile and the current journal in use is the persistent journal, then the active journal will be switched to the volatile journal.

   .. versionadded:: 258

Credentials
###########

:code:`systemd-journald` supports the service credentials logic as implemented by :code:`ImportCredential=`/:code:`LoadCredential=`/:code:`SetCredential=` (see :ref:`systemd.exec(5)` for details). The following credentials are used when passed in:

.. systemd:option:: journal.forward_to_socket
   :group: system-credentials

   May contain a socket address to which logs should be forwarded. See :systemd:var:`ForwardToSocket=` in :man-pages:`journald.conf(5)`.

   .. versionadded:: 256

.. systemd:option:: journal.storage
   :group: system-credentials

   May be used to specify where journal files should be stored. See :systemd:var:`Storage=` in :man-pages:`journald.conf(5)`.

   .. versionadded:: 256

Kernel Command Line
###################

A few configuration parameters from :code:`journald.conf` may be overridden on the kernel command line:

.. systemd:option:: systemd.journald.forward_to_syslog=, systemd.journald.forward_to_kmsg=, systemd.journald.forward_to_console=, systemd.journald.forward_to_wall=
   :group: kernel-commandline-options

   Enables/disables forwarding of collected log messages to syslog, the kernel log buffer, the system console or wall.

   See :man-pages:`journald.conf(5)` for information about these settings.

   .. versionadded:: 186

.. systemd:option:: systemd.journald.max_level_store=, systemd.journald.max_level_syslog=, systemd.journald.max_level_kmsg=, systemd.journald.max_level_console=, systemd.journald.max_level_wall=, systemd.journald.max_level_socket=
   :group: kernel-commandline-options

   Controls the maximum log level of messages that are stored in the journal, forwarded to :man-pages:`syslog(3)`, kmsg, the console, :man-pages:`wall(1)`, or a socket. This kernel command line options override the settings of the same names in the :man-pages:`journald.conf(5)` file.

   .. versionadded:: 232

Note that these kernel command line options are only honoured by the default namespace, see above.

Access Control
##############

Journal files are, by default, owned and readable by the "systemd-journal" system group but are not writable. Adding a user to this group thus enables them to read the journal files.

By default, each user, with a UID outside the range of system users, dynamic service users, and the nobody user, will get their own set of journal files in :code:`/var/log/journal/`. See `Users, Groups, UIDs and GIDs on systemd systems <https://systemd.io/UIDS-GIDS>`_ for more details about UID ranges. These journal files will not be owned by the user, however, in order to avoid that the user can write to them directly. Instead, file system ACLs are used to ensure the user gets read access only.

Additional users and groups may be granted access to journal files via file system access control lists (ACL). Distributions and administrators may choose to grant read access to all members of the "wheel" and "adm" system groups with a command such as the following:

.. code-block:: sh

   # setfacl -Rnm g:wheel:rx,d:g:wheel:rx,g:adm:rx,d:g:adm:rx /var/log/journal/

Note that this command will update the ACLs both for existing journal files and for future journal files created in the :code:`/var/log/journal/` directory.

Files
#####

.. systemd:option:: /etc/systemd/journald.conf

   Configure :code:`systemd-journald` behavior. See :man-pages:`journald.conf(5)`.

   .. versionadded:: 206

.. systemd:option:: /run/log/journal/machine-id/\*.journal, /run/log/journal/machine-id/\*.journal~, /var/log/journal/machine-id/\*.journal, /var/log/journal/machine-id/\*.journal~

   :code:`systemd-journald` writes entries to files in :code:`/run/log/journal/machine-id/` or :code:`/var/log/journal/machine-id/` with the ".journal" suffix. If the daemon is stopped uncleanly, or if the files are found to be corrupted, they are renamed using the ".journal~" suffix, and :code:`systemd-journald` starts writing to a new file. :code:`/run/` is used when :code:`/var/log/journal` is not available, or when :code:`Storage=volatile` is set in the :man-pages:`journald.conf(5)` configuration file.

   When :code:`systemd-journald` ceases writing to a journal file, it will be renamed to ":emphasis:`original-name`\@:emphasis:`suffix.journal`" (or ":emphasis:`original-name`\@:emphasis:`suffix.journal~`"). Such files are "archived" and will not be written to any more.

   In general, it is safe to read or copy any journal file (active or archived). :man-pages:`journalctl(1)` and the functions in the :ref:`sd-journal(3)` library should be able to read all entries that have been fully written.

   :code:`systemd-journald` will automatically remove the oldest archived journal files to limit disk use. See :code:`SystemMaxUse=` and related settings in :man-pages:`journald.conf(5)`.

   .. versionadded:: 206

.. systemd:option:: /dev/kmsg, /dev/log, /run/systemd/journal/dev-log, /run/systemd/journal/socket, /run/systemd/journal/stdout

   Sockets and other file node paths that :code:`systemd-journald` will listen on and are visible in the file system. In addition to these, :code:`systemd-journald` can listen for audit events using :man-pages:`netlink(7)`, depending on whether "systemd-journald-audit.socket" is enabled or not.

   .. versionadded:: 228

If journal namespacing is used these paths are slightly altered to include a namespace identifier, see above.
