================
coredump.conf(5)
================

Name
####

coredump.conf, coredump.conf.d — Core dump storage configuration files

Synopsis
########

| :code:`/etc/systemd/coredump.conf`
| :code:`/run/systemd/coredump.conf`
| :code:`/usr/local/lib/systemd/coredump.conf`
| :code:`/usr/lib/systemd/coredump.conf`
| :code:`/etc/systemd/coredump.conf.d/\*.conf`
| :code:`/run/systemd/coredump.conf.d/\*.conf`
| :code:`/usr/local/lib/systemd/coredump.conf.d/\*.conf`
| :code:`/usr/lib/systemd/coredump.conf.d/\*.conf`

Description
###########

These files configure the behavior of :ref:`systemd-coredump(8)`, a handler for core dumps invoked by the kernel. Whether :code:`systemd-coredump` is used is determined by the kernel's :code:`kernel.core_pattern` :man-pages:`sysctl(8)` setting. See :ref:`systemd-coredump(8)` and :man-pages:`core(5)` pages for the details.

Options
#######

All options are configured in the \[Coredump] section:

.. systemd:option:: Storage=
   :group: config-directives

   Controls where to store cores. One of "none", "external", and "journal". When "none", the core dumps may be logged (including the backtrace if possible), but not stored permanently. When "external" (the default), cores will be stored in :code:`/var/lib/systemd/coredump/`. When "journal", cores will be stored in the journal and rotated following normal journal rotation patterns.

   When cores are stored in the journal, they might be compressed following journal compression settings, see :man-pages:`journald.conf(5)`. When cores are stored externally, they will be compressed by default, see below.

   Note that in order to process a coredump (i.e. extract a stack trace) the core must be written to disk first. Thus, unless :systemd:var:`ProcessSizeMax=` is set to 0 (see below), the core will be written to :code:`/var/lib/systemd/coredump/` either way (under a temporary filename, or even in an unlinked file), :systemd:var:`Storage=` thus only controls whether to leave it there even after it was processed.

   .. versionadded:: 215

.. systemd:option:: Compress=
   :group: config-directives

   Controls compression for external storage. Takes a boolean argument, which defaults to "yes".

   .. versionadded:: 215

.. systemd:option:: ProcessSizeMax=
   :group: config-directives

   The maximum size in bytes of a core which will be processed. Core dumps exceeding this size may be stored, but the stack trace will not be generated. Like other sizes in this same config file, the usual suffixes to the base of 1024 are allowed (B, K, M, G, T, P, and E). Defaults to 1G on 32-bit systems, 32G on 64-bit systems.

   Setting :systemd:var:`Storage=none` and :systemd:var:`ProcessSizeMax=0` disables all coredump handling except for a log entry.

   .. versionadded:: 215

.. systemd:option:: EnterNamespace=
   :group: config-directives

   For processes belonging to a PID namespace, controls whether :ref:`systemd-coredump(8)` shall attempt to process core dumps on the host, using debug information from the file system hierarchy (i.e. the mount namespace) of the process that crashed. Access to the process' file system hierarchy might be necessary to generate a fully symbolized backtrace. If set to "yes", :code:`systemd-coredump` will obtain the tree of mounts from the crashing process' mount namespace and will try to generate the stack trace in host context using the debug information of binaries and libraries contained in the crashing process' hierarchy. Defaults to "no", i.e. no attempt is made to acquire external debug information from the process' mount namespace, in order to maximize security. This option has no effect on processes that are part of the host's PID namespace.

   Note that the coredump of the namespaced process is still saved in :code:`/var/lib/systemd/coredump/` on the host even if :systemd:var:`EnterNamespace=` is set to "no" (subject to :systemd:var:`Storage=`).

   Note that :systemd:var:`EnterNamespace=` only has an effect if a core dump is generated by a container whose unit does not have :systemd:var:`CoredumpReceive=` enabled.

   Note that it's typically preferable to let containers and other namespace-based sandboxes process their own coredumps, if possible, for best security. This may be enabled on the container's unit via the :systemd:var:`CoredumpReceive=` setting, see :ref:`systemd.resource-control(5)` for details.

   .. versionadded:: 257

.. systemd:option:: ExternalSizeMax=, JournalSizeMax=
   :group: config-directives

   The maximum (compressed or uncompressed) size in bytes of a coredump to be saved in separate files on disk (default: 1G on 32-bit systems, 32G on 64-bit systems) or in the journal (default: 767M). Note that the journal service enforces a hard limit on journal log records of 767M, and will ignore larger submitted log records. Hence, :systemd:var:`JournalSizeMax=` may be lowered relative to the default, but not increased. Unit suffixes are allowed just as in :systemd:option:`ProcessSizeMax=`.

   :systemd:var:`ExternalSizeMax=infinity` sets the core size to unlimited.

   .. versionadded:: 215

.. systemd:option:: MaxUse=, KeepFree=
   :group: config-directives

   Enforce limits on the disk space, specified in bytes, taken up by externally stored core dumps. Unit suffixes are allowed just as in :systemd:option:`ProcessSizeMax=`. :systemd:option:`MaxUse=` makes sure that old core dumps are removed as soon as the total disk space taken up by core dumps grows beyond this limit (defaults to 10% of the total disk size). :systemd:option:`KeepFree=` controls how much disk space to keep free at least (defaults to 15% of the total disk size). Note that the disk space used by core dumps might temporarily exceed these limits while core dumps are processed. Note that old core dumps are also removed based on time via :ref:`systemd-tmpfiles(8)`. Set either value to 0 to turn off size-based cleanup.

   .. versionadded:: 215

Use

.. code-block:: sh

   systemd-analyze cat-config systemd/coredump.conf

to display the full config.
