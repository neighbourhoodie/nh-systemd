===================
systemd-coredump(8)
===================

Name
####

systemd-coredump, systemd-coredump.socket, systemd-coredump@.service — Acquire, save and process core dumps

Synopsis
########

:code:`/usr/lib/systemd/systemd-coredump`

:code:`/usr/lib/systemd/systemd-coredump` :code:`--backtrace`

:code:`systemd-coredump@.service`

:code:`systemd-coredump.socket`

Description
###########

:code:`systemd-coredump@.service` is a system service to process core dumps. It will log a summary of the event to :ref:`systemd-journald.service(8)`, including information about the process identifier, owner, the signal that killed the process, and the stack trace if possible. It may also save the core dump for later processing. See the "Information about the crashed process" section below.

The behavior of a specific program upon reception of a signal is governed by a few factors which are described in detail in :man-pages:`core(5)`. In particular, the core dump will only be processed when the related process resource limits (:code:`RLIMIT_CORE`) are sufficient.

Core dumps can be written to the journal or saved as a file. In both cases, they can be retrieved for further processing, for example in :man-pages:`gdb(1)`. See :man-pages:`coredumpctl(1)`, in particular the :code:`list` and :code:`debug` verbs.

By default, :code:`systemd-coredump` will log the core dump to the journal, including a backtrace if possible, and store the core dump (an image of the memory contents of the process) itself in an external file in :code:`/var/lib/systemd/coredump/`. These core dumps are deleted after a few days by default; see :code:`/usr/lib/tmpfiles.d/systemd.conf` for details. Note that the removal of core files from the file system and the purging of journal entries are independent, and the core file may be present without the journal entry, and journal entries may point to since-removed core files. Some metadata is attached to core files in the form of extended attributes, so the core files are useful for some purposes even without the full metadata available in the journal entry.

For further details see `systemd Coredump Handling <https://systemd.io/COREDUMP>`_.

Invocation of :code:`systemd-coredump`
######################################

The :code:`systemd-coredump` executable does the actual work. It is invoked twice: once as the handler by the kernel, and the second time in the :code:`systemd-coredump@.service` to actually write the data to the journal and process and save the core file.

When the kernel invokes :code:`systemd-coredump` to handle a core dump, it runs in privileged mode, and will connect to the socket created by the :code:`systemd-coredump.socket` unit, which in turn will spawn an unprivileged :code:`systemd-coredump@.service` instance to process the core dump. Hence :code:`systemd-coredump.socket` and :code:`systemd-coredump@.service` are helper units which do the actual processing of core dumps and are subject to normal service management.

It is also possible to invoke :code:`systemd-coredump` with :code:`--backtrace` option. In this case, :code:`systemd-coredump` expects a journal entry in the journal `Journal Export Format <https://systemd.io/JOURNAL_EXPORT_FORMATS#journal-export-format>`_ on standard input. The entry should contain a :code:`MESSAGE=` field and any additional metadata fields the caller deems reasonable. :code:`systemd-coredump` will append additional metadata fields in the same way it does for core dumps received from the kernel. In this mode, no core dump is stored in the journal.

Core dumps in Containers/Namespaces
###################################

The :code:`systemd-coredump@.service` service will automatically attempt to extract a stacktrace from a process as it crashes. For this stacktrace symbols will be resolved based on debug information embedded in the crashing ELF image, or equivalent debug information separately available on the host OS. For processes that crash inside of local containers or other mount namespace-based sandboxes, this auxiliary debug information is typically not available on the host (simply because containers typically run different software versions than the host). :code:`systemd-coredump` provides two mechanisms to address this:

1.    For full-OS containers running systemd inside it is a good idea to enable :code:`CoredumpReceive=` on the unit (see :ref:`systemd.resource-control(5)`), which ensures that coredumps of a container are attempted to be forwarded to :code:`systemd-coredump@.service` running inside the container, i.e the container gets to process and store its own core dumps. Note that :ref:`systemd-nspawn(8)` defaults to this mode if invoked with the :code:`--boot` switch. This mode of operation is generally recommended for security reasons: the security-sensitive processing of the core dump is done within the confinements of the container itself, by the container's own code, backed by the container's own storage.

2.    Alternatively, for more restricted containers (that do not run a proper :code:`init` system as PID 1) it is possible to enable processing of the core dump on the host, with access to the debug information data from the container itself. This mode of operation must be enabled via :code:`EnterNamespace=` in :man-pages:`coredump.conf(5)`, and defaults to off, for security reasons.

If both :code:`CoredumpReceive=` is enabled on the unit of the container the core dump belongs to, and :code:`EnterNamespace=` is enabled in the :code:`coredump.conf` configuration file, the former takes precedence.

Configuration
#############

For programs started by :code:`systemd`, process resource limits can be set by directive :code:`LimitCORE=`, see :ref:`systemd.exec(5)`.

In order to be used by the kernel to handle core dumps, :code:`systemd-coredump` must be configured in :man-pages:`sysctl(8)` parameter :code:`kernel.core_pattern`. The syntax of this parameter is explained in :man-pages:`core(5)`. systemd installs the file :code:`/usr/lib/sysctl.d/50-coredump.conf` which configures :code:`kernel.core_pattern` accordingly. This file may be masked or overridden to use a different setting following normal :man-pages:`sysctl.d(5)` rules. If the sysctl configuration is modified, it must be updated in the kernel before it takes effect, see :man-pages:`sysctl(8)` and :ref:`systemd-sysctl(8)`.

In order to be used in the :code:`--backtrace` mode, an appropriate backtrace handler must be installed on the sender side. For example, in case of :die-net:`python(1)`, this means a :code:`sys.excepthook` must be installed, see `systemd-coredump-python <https://github.com/systemd/systemd-coredump-python>`_.

The behavior of :code:`systemd-coredump` itself is configured through the configuration file :code:`/etc/systemd/coredump.conf` and corresponding snippets :code:`/etc/systemd/coredump.conf.d/\*.conf`, see :man-pages:`coredump.conf(5)`. A new instance of :code:`systemd-coredump` is invoked upon receiving every core dump. Therefore, changes in these files will take effect the next time a core dump is received.

Resources used by core dump files are restricted in two ways. Parameters like maximum size of acquired core dumps and files can be set in files :code:`/etc/systemd/coredump.conf` and snippets mentioned above. In addition the storage time of core dump files is restricted by :code:`systemd-tmpfiles`, corresponding settings are by default in :code:`/usr/lib/tmpfiles.d/systemd.conf`. The default is to delete core dumps after a few days; see the above file for details.

Disabling coredump processing
#############################

To disable potentially resource-intensive processing by :code:`systemd-coredump`, set

.. code-block:: sh

   Storage=none
   ProcessSizeMax=0

in :man-pages:`coredump.conf(5)`.

Information about the crashed process
#####################################

:man-pages:`coredumpctl(1)` can be used to retrieve saved core dumps independently of their location, to display information, and to process them e.g. by passing to the GNU debugger (gdb).

Data stored in the journal can be also viewed with :man-pages:`journalctl(1)` as usual (or from any other process, using the :ref:`sd-journal(3)` API). The relevant messages have :code:`MESSAGE_ID=fc2e22bc6ee647b6b90729ab34a250b1`:

.. code-block:: sh

   $ journalctl MESSAGE_ID=fc2e22bc6ee647b6b90729ab34a250b1 -o verbose
   …
   MESSAGE_ID=fc2e22bc6ee647b6b90729ab34a250b1
   COREDUMP_PID=552351
   COREDUMP_UID=1000
   COREDUMP_GID=1000
   COREDUMP_SIGNAL_NAME=SIGSEGV
   COREDUMP_SIGNAL=11
   COREDUMP_TIMESTAMP=1614342930000000
   COREDUMP_COMM=Web Content
   COREDUMP_EXE=/usr/lib64/firefox/firefox
   COREDUMP_USER_UNIT=app-gnome-firefox-552136.scope
   COREDUMP_CMDLINE=/usr/lib64/firefox/firefox -contentproc -childID 5 -isForBrowser …
   COREDUMP_CGROUP=/user.slice/user-1000.slice/user@1000.service/app.slice/app-….scope
   COREDUMP_FILENAME=/var/lib/systemd/coredump/core.Web….552351.….zst
   …

The following fields are saved (if known) with the journal entry

.. systemd:option:: COREDUMP_UID=, COREDUMP_PID=, COREDUMP_GID=
   :group: journal-directives

   The process number (PID), owner user number (UID), and group number (GID) of the crashed process.

   When the crashed process was part of a container (or in a process or user namespace in general), those are the values as seen *outside*\, in the namespace where , in the namespace where :code:`systemd-coredump` is running.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_BY_PIDFD=
   :group: journal-directives

   If the crashed process was analyzed using a PIDFD provided by the kernel (requires kernel v6.16) then this field will be present and set to "1". If this field is not set, then the crashed process was analyzed via a PID, which is known to be subject to race conditions.

   .. versionadded:: 258

.. systemd:option:: COREDUMP_TIMESTAMP=
   :group: journal-directives

   The time of the crash as reported by the kernel (in μs since the epoch).

   .. versionadded:: 248

.. systemd:option:: COREDUMP_RLIMIT=
   :group: journal-directives

   The core file size soft resource limit, see :man-pages:`getrlimit(2)`.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_UNIT=, COREDUMP_SLICE=
   :group: journal-directives

   The system unit and slice names.

   When the crashed process was in container, those are the units names *outside*\, in the main system manager., in the main system manager.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_CGROUP=
   :group: journal-directives

   The primary cgroup of the unit of the crashed process.

   When the crashed process was in a container, this is the full path, as seen outside of the container.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_PROC_CGROUP=
   :group: journal-directives

   Control group information in the format used in :code:`/proc/self/cgroup`. On systems with the unified cgroup hierarchy, this is a single path prefixed with "0::", and multiple paths prefixed with controller numbers on legacy systems.

   When the crashed process was in a container, this is the full path, as seen outside of the container.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_OWNER_UID=, COREDUMP_USER_UNIT=, COREDUMP_SESSION=
   :group: journal-directives

   The numerical UID of the user owning the login session or systemd user unit of the crashed process, the user manager unit, and the session identifier. All three fields are only present for user processes.

   When the crashed process was in container, those are the values *outside*\, in the main system., in the main system.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_SIGNAL_NAME=, COREDUMP_SIGNAL=
   :group: journal-directives

   The terminating signal name (with the "SIG" prefix  [#]_ ) and numerical value. (Both are included because signal numbers vary by architecture.)

   .. versionadded:: 248

.. systemd:option:: COREDUMP_CWD=, COREDUMP_ROOT=
   :group: journal-directives

   The current working directory and root directory of the crashed process.

   When the crashed process is in a container, those paths are relative to the root of the container's mount namespace.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_DUMPABLE=
   :group: journal-directives

   The :systemd:constant:`PR_GET_DUMPABLE` field as reported by the kernel, see :man-pages:`prctl(2)`.

   .. versionadded:: 258

.. systemd:option:: COREDUMP_OPEN_FDS=
   :group: journal-directives

   Information about open file descriptors, in the following format:

     .. code-block:: sh

        fd:/path/to/file
        pos:     ...
        flags:   ...
        ...
        fd:/path/to/file
        pos:     ...
        flags:   ...
        ...

   The first line contains the file descriptor number :emphasis:`fd` and the path, while subsequent lines show the contents of :code:`/proc/pid/fdinfo/fd`.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_EXE=
   :group: journal-directives

   The destination of the :code:`/proc/pid/exe` symlink.

   When the crashed process is in a container, that path is relative to the root of the container's mount namespace.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_CMDLINE=, COREDUMP_COMM=, COREDUMP_ENVIRON=, COREDUMP_PROC_AUXV=, COREDUMP_PROC_LIMITS=, COREDUMP_PROC_MAPS=, COREDUMP_PROC_MOUNTINFO=, COREDUMP_PROC_STATUS=
   :group: journal-directives

   Fields that map the per-process entries in the :code:`/proc/` filesystem: :code:`/proc/pid/cmdline` (the command line of the crashed process), :code:`/proc/pid/comm` (the command name associated with the process), :code:`/proc/pid/environ` (the environment block of the crashed process), :code:`/proc/pid/auxv` (the auxiliary vector of the crashed process, see :man-pages:`getauxval(3)`), :code:`/proc/pid/limits` (the soft and hard resource limits), :code:`/proc/pid/maps` (memory regions visible to the process and their access permissions), :code:`/proc/pid/mountinfo` (mount points in the process's mount namespace), :code:`/proc/pid/status` (various metadata about the process).

   See :man-pages:`proc(5)` for more information.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_HOSTNAME=
   :group: journal-directives

   The system hostname.

   When the crashed process was in container, this is the container hostname.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_CONTAINER_CMDLINE=
   :group: journal-directives

   For processes running in a container, the command line of the process spawning the container (the first parent process with a different mount namespace).

   .. versionadded:: 248

.. systemd:option:: COREDUMP=
   :group: journal-directives

   When the core is stored in the journal, the core image itself.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_FILENAME=
   :group: journal-directives

   When the core is stored externally, the path to the core file.

   .. versionadded:: 248

.. systemd:option:: COREDUMP_TRUNCATED=
   :group: journal-directives

   Set to "1" when the saved coredump was truncated. (A partial core image may still be processed by some tools, though obviously not all information is available.)

   .. versionadded:: 248

.. systemd:option:: COREDUMP_PACKAGE_NAME=, COREDUMP_PACKAGE_VERSION=, COREDUMP_PACKAGE_JSON=
   :group: journal-directives

   If the executable contained .package metadata ELF notes, they will be parsed and attached. The :systemd:var:`package` and :systemd:var:`version` of the 'main' ELF module (i.e., the executable) will be appended individually. The JSON-formatted content of all modules will be appended as a single JSON object, each with the module name as the key. For more information about this metadata format and content, see the `Package Metadata for Executable Files <https://systemd.io/PACKAGE_METADATA_FOR_EXECUTABLE_FILES/>`_ document.

   .. versionadded:: 249

.. systemd:option:: MESSAGE=
   :group: journal-directives

   The message generated by :code:`systemd-coredump` that includes the backtrace if it was successfully generated. When :code:`systemd-coredump` is invoked with :systemd:option:`--backtrace`, this field is provided by the caller.

   .. versionadded:: 248

Various other fields exist in the journal entry, but pertain to the logging process, i.e. :code:`systemd-coredump`, not the crashed process. See :ref:`systemd.journal-fields(7)`.

The following fields are saved (if known) with the external file listed in :code:`COREDUMP_FILENAME=` as extended attributes:

.. systemd:option:: user.coredump.pid, user.coredump.uid, user.coredump.gid, user.coredump.signal, user.coredump.timestamp, user.coredump.rlimit, user.coredump.hostname, user.coredump.comm, user.coredump.exe

   Those are the same as :code:`COREDUMP_PID=`, :code:`COREDUMP_UID=`, :code:`COREDUMP_GID=`, :code:`COREDUMP_SIGNAL=`, :code:`COREDUMP_TIMESTAMP=`, :code:`COREDUMP_RLIMIT=`, :code:`COREDUMP_HOSTNAME=`, :code:`COREDUMP_COMM=`, and :code:`COREDUMP_EXE=`, described above.

   .. versionadded:: 248

Those can be viewed using :man-pages:`getfattr(1)`. For the core file described in the journal entry shown above:

.. code-block:: sh

   $ getfattr --absolute-names -d /var/lib/systemd/coredump/core.Web….552351.….zst
   # file: /var/lib/systemd/coredump/core.Web….552351.….zst
   user.coredump.pid="552351"
   user.coredump.uid="1000"
   user.coredump.gid="1000"
   user.coredump.signal="11"
   user.coredump.timestamp="1614342930000000"
   user.coredump.comm="Web Content"
   user.coredump.exe="/usr/lib64/firefox/firefox"
   …
