==============
systemd-run(1)
==============

Name
####

systemd-run — Run programs in transient scope units, service units, or path-, socket-, or timer-triggered service units

Synopsis
########

:code:`systemd-run [OPTIONS...] COMMAND [ARGS...]`

:code:`systemd-run [OPTIONS...] [PATH OPTIONS...] {COMMAND[ARGS...]}`

:code:`systemd-run [OPTIONS...] [SOCKET OPTIONS...] {COMMAND[ARGS...]}`

:code:`systemd-run [OPTIONS...] [TIMER OPTIONS...] {COMMAND[ARGS...]}`

Description
###########

:code:`systemd-run` may be used to create and start a transient :code:`.service` or :code:`.scope` unit and run the specified :emphasis:`COMMAND` in it. It may also be used to create and start a transient :code:`.path`, :code:`.socket`, or :code:`.timer` unit, that activates a :code:`.service` unit when elapsing.

If a command is run as transient service unit, it will be started and managed by the service manager like any other service, and thus shows up in the output of :code:`systemctl list-units` like any other unit. It will run in a clean and detached execution environment, with the service manager as its parent process. In this mode, :code:`systemd-run` will start the service asynchronously in the background and return after the command has begun execution (unless :code:`--no-block`, :code:`--wait`, :code:`--pipe`, or :code:`--pty` are specified, see below).

If a command is run as transient scope unit, it will be executed by :code:`systemd-run` itself as parent process and will thus inherit the execution environment of the caller. However, the processes of the command are managed by the service manager similarly to normal services, and will show up in the output of :code:`systemctl list-units`. Execution in this case is synchronous, and will return only when the command finishes. This mode is enabled via the :code:`--scope` switch (see below).

If a command is run with path, socket, or timer options such as :code:`--on-calendar=` (see below), a transient path, socket, or timer unit is created alongside the service unit for the specified command. Only the transient path, socket, or timer unit is started immediately, the transient service unit will be triggered by the path, socket, or timer unit. If the :code:`--unit=` option is specified, the :emphasis:`COMMAND` may be omitted. In this case, :code:`systemd-run` creates only a :code:`.path`, :code:`.socket`, or :code:`.timer` unit that triggers the specified unit.

By default, services created with :code:`systemd-run` default to the :code:`simple` type, see the description of :code:`Type=` in :ref:`systemd.service(5)` for details. Note that when this type is used, the service manager (and thus the :code:`systemd-run` command) considers service start-up successful as soon as the :code:`fork()` for the main service process succeeded, i.e. before the :code:`execve()` is invoked, and thus even if the specified command cannot be started. Consider using the :code:`exec` service type (i.e. :code:`--property=Type=exec`) to ensure that :code:`systemd-run` returns successfully only if the specified command line has been successfully started.

After :code:`systemd-run` passes the command to the service manager, the manager performs variable expansion. This means that dollar characters ("$") which should not be expanded need to be escaped as "$$". Expansion can also be disabled using :code:`--expand-environment=no`.

Options
#######

The following options are understood:

.. systemd:option:: --scope

   Create a transient :code:`.scope` unit instead of the default transient :code:`.service` unit (see above).

   .. versionadded:: 206

.. systemd:option:: --unit=, -u

   Use this unit name instead of an automatically generated one.

   .. versionadded:: 206

.. systemd:option:: --property=, -p

   Sets a property on the scope or service unit that is created. This option takes an assignment in the same format as :man-pages:`systemctl(1)`'s :code:`set-property` command.

   .. versionadded:: 211

.. systemd:option:: --description=

   Provide a description for the service, scope, path, socket, or timer unit. If not specified, the command itself will be used as a description. See :code:`Description=` in :ref:`systemd.unit(5)`.

   .. versionadded:: 206

.. systemd:option:: --slice=

   Make the new :code:`.service` or :code:`.scope` unit part of the specified slice, instead of :code:`system.slice` (when running in :code:`--system` mode) or the root slice (when running in :code:`--user` mode).

   .. versionadded:: 206

.. systemd:option:: --slice-inherit

   Make the new :code:`.service` or :code:`.scope` unit part of the slice the :code:`systemd-run` itself has been invoked in. This option may be combined with :code:`--slice=`, in which case the slice specified via :code:`--slice=` is placed within the slice the :code:`systemd-run` command is invoked in.

   Example: consider :code:`systemd-run` being invoked in the slice :code:`foo.slice`, and the :code:`--slice=` argument is :code:`bar`. The unit will then be placed under :code:`foo-bar.slice`.

   .. versionadded:: 246

.. systemd:option:: --expand-environment=BOOL

   Expand environment variables in command arguments. If enabled (the default), environment variables specified as "${:emphasis:`VARIABLE`}" will be expanded in the same way as in commands specified via :code:`ExecStart=` in units. With :code:`--scope`, this expansion is performed by :code:`systemd-run` itself, and in other cases by the service manager that spawns the command. Note that this is similar to, but not the same as variable expansion in :man-pages:`bash(1)` and other shells.

   See :ref:`systemd.service(5)` for a description of variable expansion. Disabling variable expansion is useful if the specified command includes or may include a "$" sign.

   .. versionadded:: 254

.. systemd:option:: -r, --remain-after-exit

   After the service process has terminated, keep the service around until it is explicitly stopped. This is useful to collect runtime information about the service after it finished running. Also see :code:`RemainAfterExit=` in :ref:`systemd.service(5)`.

   .. versionadded:: 207

.. systemd:option:: --send-sighup

   When terminating the scope or service unit, send a SIGHUP immediately after SIGTERM. This is useful to indicate to shells and shell-like processes that the connection has been severed. Also see :code:`SendSIGHUP=` in :ref:`systemd.kill(5)`.

   .. versionadded:: 207

.. systemd:option:: --service-type=

   Sets the service type. Also see :code:`Type=` in :ref:`systemd.service(5)`. This option has no effect in conjunction with :code:`--scope`. Defaults to :code:`simple`.

   .. versionadded:: 211

.. systemd:option:: --uid=, --gid=

   Runs the service process under the specified UNIX user and group. Also see :code:`User=` and :code:`Group=` in :ref:`systemd.exec(5)`.

   .. versionadded:: 211

.. systemd:option:: --nice=

   Runs the service process with the specified nice level. Also see :code:`Nice=` in :ref:`systemd.exec(5)`.

   .. versionadded:: 211

.. systemd:option:: --working-directory=

   Runs the service process with the specified working directory. Also see :code:`WorkingDirectory=` in :ref:`systemd.exec(5)`.

   .. versionadded:: 240

.. systemd:option:: --same-dir, -d

   Similar to :code:`--working-directory=`, but uses the current working directory of the caller for the service to execute.

   .. versionadded:: 240

.. systemd:option:: --root-directory=

   Runs the service process with the specified root directory. Also see :code:`RootDirectory=` in :ref:`systemd.exec(5)`.

   Note that the path is looked up inside the file system namespace that systemd-run is running in, which might be different that the file system namespace the manager process is running in. Use the :code:`RootDirectory=` property directly if you want the path to be looked up in the manager process's file system namespace.

   .. versionadded:: 259

.. systemd:option:: --same-root-dir, -R

   Similar to :code:`--root-directory=`, but uses the root directory of the systemd-run process as the root directory to execute the service in.

   .. versionadded:: 259

.. systemd:option:: -E NAME[=VALUE], --setenv=NAME[=VALUE]

   Runs the service process with the specified environment variable set. This parameter may be used more than once to set multiple variables. When "=" and :emphasis:`VALUE` are omitted, the value of the variable with the same name in the program environment will be used.

   Also see :code:`Environment=` in :ref:`systemd.exec(5)`.

   .. versionadded:: 211

.. systemd:option:: --pty, -t

   When invoking the command, the transient service connects its standard input, output and error to the terminal :code:`systemd-run` is invoked on, via a pseudo TTY device. This allows running programs that expect interactive user input/output as services, such as interactive command shells.

   This option will result in :code:`systemd-run` synchronously waiting for the transient service to terminate, similar to specifying :code:`--wait`. If specified along with :code:`--wait`, :code:`systemd-run` will not exit when manually disconnecting from the pseudo TTY device.

   Note that :man-pages:`machinectl(1)`'s :code:`shell` command is usually a better alternative for requesting a new, interactive login session on the local host or a local container.

   See below for details on how this switch combines with :code:`--pipe`.

   .. versionadded:: 219

.. systemd:option:: --pty-late, -T

   Much like :code:`--pty`, but the PTY communication only begins once the unit start is complete. This effectively means PTY input during :code:`ExecStartPre=` of a service is not available while using :code:`--pty-late`, while it is available using :code:`--pty`, for most service types. However, if this option is used, access to the invoking TTY is available for password queries (see :code:`--no-ask-password` below) during unit start-up.

   .. versionadded:: 258

.. systemd:option:: --pipe, -P

   If specified, standard input, output, and error of the transient service are inherited from the :code:`systemd-run` command itself. This allows :code:`systemd-run` to be used within shell pipelines.

   Note that this mode is not suitable for interactive command shells and similar, as the service process will not become a TTY controller when invoked on a terminal. Use :code:`--pty` instead in that case.

   When both :code:`--pipe` and :code:`--pty` are used in combination the more appropriate option is automatically determined and used. Specifically, when invoked with standard input, output and error connected to a TTY :code:`--pty` is used, and otherwise :code:`--pipe`.

   This option will result in :code:`systemd-run` synchronously waiting for the transient service to terminate, similar to specifying :code:`--wait`.

   When this option is used the original file descriptors :code:`systemd-run` receives are passed to the service processes as-is. If the service runs with different privileges than :code:`systemd-run`, this means the service might not be able to reopen the passed file descriptors, due to normal file descriptor access restrictions. If the invoked process is a shell script that uses the :code:`echo "hello" >/dev/stderr` construct for writing messages to stderr, this might cause problems, as this only works if stderr can be reopened. To mitigate this use the construct :code:`echo "hello" >&2` instead, which is mostly equivalent and avoids this pitfall.

   .. versionadded:: 235

.. systemd:option:: --shell, -S

   A shortcut for "--pty --same-dir --wait --collect --service-type=exec $SHELL", i.e. requests an interactive shell in the current working directory, running in service context, accessible with a single switch.

   .. versionadded:: 240

.. systemd:option:: --quiet, -q

   Suppresses additional informational output while running. This is particularly useful in combination with :code:`--pty` when it will suppress the initial message explaining how to terminate the TTY connection.

   .. versionadded:: 219

.. systemd:option:: -v, --verbose

   Display unit log output while running.

   .. versionadded:: 258

.. systemd:option:: --on-active=, --on-boot=, --on-startup=, --on-unit-active=, --on-unit-inactive=

   Defines a monotonic timer relative to different starting points for starting the specified command. See :code:`OnActiveSec=`, :code:`OnBootSec=`, :code:`OnStartupSec=`, :code:`OnUnitActiveSec=` and :code:`OnUnitInactiveSec=` in :ref:`systemd.timer(5)` for details. These options are shortcuts for :code:`--timer-property=` with the relevant properties. These options may not be combined with :code:`--scope` or :code:`--pty`.

   .. versionadded:: 218

.. systemd:option:: --on-calendar=

   Defines a calendar timer for starting the specified command. See :code:`OnCalendar=` in :ref:`systemd.timer(5)`. This option is a shortcut for :code:`--timer-property=OnCalendar=`. This option may not be combined with :code:`--scope` or :code:`--pty`.

   .. versionadded:: 218

.. systemd:option:: --on-clock-change, --on-timezone-change

   Defines a trigger based on system clock jumps or timezone changes for starting the specified command. See :code:`OnClockChange=` and :code:`OnTimezoneChange=` in :ref:`systemd.timer(5)`. These options are shortcuts for :code:`--timer-property=OnClockChange=yes` and :code:`--timer-property=OnTimezoneChange=yes`. These options may not be combined with :code:`--scope` or :code:`--pty`.

   .. versionadded:: 242

.. systemd:option:: --path-property=, --socket-property=, --timer-property=

   Sets a property on the path, socket, or timer unit that is created. This option is similar to :code:`--property=`, but applies to the transient path, socket, or timer unit rather than the transient service unit created. This option takes an assignment in the same format as :man-pages:`systemctl(1)`'s :code:`set-property` command. These options may not be combined with :code:`--scope` or :code:`--pty`.

   .. versionadded:: 218

.. systemd:option:: --no-block

   Do not synchronously wait for the unit start operation to finish. If this option is not specified, the start request for the transient unit will be verified, enqueued and :code:`systemd-run` will wait until the unit's start-up is completed. By passing this argument, it is only verified and enqueued. This option may not be combined with :code:`--wait`.

   .. versionadded:: 220

.. systemd:option:: --wait

   Synchronously wait for the transient service to terminate. If this option is specified, the start request for the transient unit is verified, enqueued, and waited for. Subsequently the invoked unit is monitored, and it is waited until it is deactivated again (most likely because the specified command completed). On exit, terse information about the unit's runtime is shown, including total runtime (as well as CPU, memory, IO, and IP accounting data, if the corresponding cgroup accounting settings are enabled) and the exit code and status of the main process. This output may be suppressed with :code:`--quiet`. This option may not be combined with :code:`--no-block`, :code:`--scope` or the various path, socket, or timer options.

   .. versionadded:: 232

.. systemd:option:: -G, --collect

   Unload the transient unit after it completed, even if it failed. Normally, without this option, all units that ran and failed are kept in memory until the user explicitly resets their failure state with :code:`systemctl reset-failed` or an equivalent command. On the other hand, units that ran successfully are unloaded immediately. If this option is turned on the "garbage collection" of units is more aggressive, and unloads units regardless of whether they exited successfully or failed. This option is a shortcut for :code:`--property=CollectMode=inactive-or-failed`, see the explanation for :code:`CollectMode=` in :ref:`systemd.unit(5)` for further information.

   .. versionadded:: 236

.. systemd:option:: --job-mode=MODE

   When queuing a new job, this option controls how to deal with already queued jobs.

   The option takes the same mode values as :man-pages:`systemctl(1)`'s :code:`--job-mode=` option. The default job mode is "fail".

   Running :code:`--job-mode=help` shows a list of available job modes.

   .. versionadded:: 258

.. systemd:option:: --ignore-failure

   By default, if the specified command fails the invoked unit will be marked failed (though possibly still unloaded, see :code:`--collect=`, above), and this is reported in the logs. If this switch is specified this is suppressed and any non-success exit status/code of the command is treated as success.

   .. versionadded:: 256

.. systemd:option:: --background=COLOR

   Change the terminal background color to the specified ANSI color as long as the session lasts. The color specified should be an ANSI X3.64 SGR background color, i.e. strings such as "40", "41", …, "47", "48;2;…", "48;5;…". See `ANSI Escape Code (Wikipedia) <https://en.wikipedia.org/wiki/ANSI_escape_code#SGR_(Select_Graphic_Rendition)_parameters>`_ for details.

   .. versionadded:: 256

All command line arguments after the first non-option argument become part of the command line of the launched process.

Exit status
###########

On success, 0 is returned. If :code:`systemd-run` failed to start the service, a non-zero return value will be returned. If :code:`systemd-run` waits for the service to terminate, the return value will be propagated from the service. 0 will be returned on success, including all the cases where systemd considers a service to have exited cleanly, see the discussion of :code:`SuccessExitStatus=` in :ref:`systemd.service(5)`.

Examples
########

Logging environment variables provided by systemd to services
-------------------------------------------------------------

.. code-block:: sh

   # systemd-run env
   Running as unit: run-19945.service
   # journalctl -u run-19945.service
   Sep 08 07:37:21 bupkis systemd[1]: Starting /usr/bin/env...
   Sep 08 07:37:21 bupkis systemd[1]: Started /usr/bin/env.
   Sep 08 07:37:21 bupkis env[19948]: PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin
   Sep 08 07:37:21 bupkis env[19948]: LANG=en_US.UTF-8
   Sep 08 07:37:21 bupkis env[19948]: BOOT_IMAGE=/vmlinuz-3.11.0-0.rc5.git6.2.fc20.x86_64

Limiting resources available to a command
-----------------------------------------

.. code-block:: sh

   # systemd-run -p IOWeight=10 updatedb

This command invokes the :man-pages:`updatedb(8)` tool, but lowers the block I/O weight for it to 10. See :ref:`systemd.resource-control(5)` for more information on the :code:`IOWeight=` property.

Running commands at a specified time
------------------------------------

The following command will touch a file after 30 seconds.

.. code-block:: sh

   # date; systemd-run --on-active=30 --timer-property=AccuracySec=100ms /bin/touch /tmp/foo
   Mon Dec  8 20:44:24 KST 2014
   Running as unit: run-71.timer
   Will run service as unit: run-71.service
   # journalctl -b -u run-71.timer
   -- Journal begins at Fri 2014-12-05 19:09:21 KST, ends at Mon 2014-12-08 20:44:54 KST. --
   Dec 08 20:44:38 container systemd[1]: Starting /bin/touch /tmp/foo.
   Dec 08 20:44:38 container systemd[1]: Started /bin/touch /tmp/foo.
   # journalctl -b -u run-71.service
   -- Journal begins at Fri 2014-12-05 19:09:21 KST, ends at Mon 2014-12-08 20:44:54 KST. --
   Dec 08 20:44:48 container systemd[1]: Starting /bin/touch /tmp/foo...
   Dec 08 20:44:48 container systemd[1]: Started /bin/touch /tmp/foo.

Allowing access to the tty
--------------------------

The following command invokes :man-pages:`bash(1)` as a service passing its standard input, output and error to the calling TTY.

.. code-block:: sh

   # systemd-run -t --send-sighup bash

Start :code:`screen` as a user service
--------------------------------------

.. code-block:: sh

   $ systemd-run --scope --user screen
   Running scope as unit run-r14b0047ab6df45bfb45e7786cc839e76.scope.
   $ screen -ls
   There is a screen on:
           492..laptop     (Detached)
   1 Socket in /var/run/screen/S-fatima.

This starts the :code:`screen` process as a child of the :code:`systemd --user` process that was started by :code:`user@.service`, in a scope unit. A :ref:`systemd.scope(5)` unit is used instead of a :ref:`systemd.service(5)` unit, because :code:`screen` will exit when detaching from the terminal, and a service unit would be terminated. Running :code:`screen` as a user unit has the advantage that it is not part of the session scope. If :code:`KillUserProcesses=yes` is configured in :man-pages:`logind.conf(5)`, the default, the session scope will be terminated when the user logs out of that session.

The :code:`user@.service` is started automatically when the user first logs in, and stays around as long as at least one login session is open. After the user logs out of the last session, :code:`user@.service` and all services underneath it are terminated. This behavior is the default, when "lingering" is not enabled for that user. Enabling lingering means that :code:`user@.service` is started automatically during boot, even if the user is not logged in, and that the service is not terminated when the user logs out.

Enabling lingering allows the user to run processes without being logged in, for example to allow :code:`screen` to persist after the user logs out, even if the session scope is terminated. In the default configuration, users can enable lingering for themselves:

.. code-block:: sh

   $ loginctl enable-linger

Variable expansion by the manager
---------------------------------

.. code-block:: sh

   $ systemd-run -t echo "<${INVOCATION_ID}>" '<${INVOCATION_ID}>'
         <> <5d0149bfa2c34b79bccb13074001eb20>

The first argument is expanded by the shell (double quotes), but the second one is not expanded by the shell (single quotes). :man-pages:`echo(1)` is called with ["/usr/bin/echo", "<>", "<${INVOCATION_ID}>"] as the argument array, and then :ref:`systemd(1)` generates :code:`${INVOCATION_ID}` and substitutes it in the command-line. This substitution could not be done on the client side, because the target ID that will be set for the service is not known before the call is made.

Variable expansion and output redirection using a shell
-------------------------------------------------------

Variable expansion by :ref:`systemd(1)` can be disabled with :code:`--expand-environment=no`.

Disabling variable expansion can be useful if the command to execute contains dollar characters and escaping them would be inconvenient. For example, when a shell is used:

.. code-block:: sh

   $ systemd-run --expand-environment=no -t bash \
         -c 'echo $SHELL $$ >/dev/stdout'
   /bin/bash 12345

The last argument is passed verbatim to the :man-pages:`bash(1)` shell which is started by the service unit. The shell expands "$SHELL" to the path of the shell, and "$$" to its process number, and then those strings are passed to the :code:`echo` built-in and printed to standard output (which, in this case, is connected to the calling terminal).

Return value
------------

.. code-block:: sh

   $ systemd-run --user --wait true
   $ systemd-run --user --wait -p SuccessExitStatus=11 bash -c 'exit 11'
   $ systemd-run --user --wait -p SuccessExitStatus=SIGUSR1 --expand-environment=no \
         bash -c 'kill -SIGUSR1 $$'

Those three invocations will succeed, i.e. terminate with an exit code of 0.
