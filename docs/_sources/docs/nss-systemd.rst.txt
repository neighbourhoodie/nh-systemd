==============
nss-systemd(8)
==============

Name
####

nss-systemd, libnss_systemd.so.2 — UNIX user and group name resolution for user/group lookup via Varlink

Synopsis
########

:code:`libnss_systemd.so.2`

Description
###########

:code:`nss-systemd` is a plug-in module for the GNU Name Service Switch (NSS) functionality of the GNU C Library (:code:`glibc`), providing UNIX user and group name resolution for services implementing the `User/Group Record Lookup API via Varlink <https://systemd.io/USER_GROUP_API>`_, such as the system and service manager :ref:`systemd(1)` (for its :code:`DynamicUser=` feature, see :ref:`systemd.exec(5)` for details), :ref:`systemd-homed.service(8)`, or :ref:`systemd-machined.service(8)`.

This module also ensures that the root and nobody users and groups (i.e. the users/groups with the UIDs/GIDs 0 and 65534) remain resolvable at all times, even if they are not listed in :code:`/etc/passwd` or :code:`/etc/group`, or if these files are missing.

This module preferably utilizes :ref:`systemd-userdbd.service(8)` for resolving users and groups, but also works without the service running.

To activate the NSS module, add "systemd" to the lines starting with "passwd:", "group:", "shadow:" and "gshadow:" in :code:`/etc/nsswitch.conf`.

It is recommended to place "systemd" after the "files" entry of the :code:`/etc/nsswitch.conf` lines so that :code:`/etc/passwd`, :code:`/etc/group`, :code:`/etc/shadow` and :code:`/etc/gshadow` based mappings take precedence.

Static Drop-In JSON User/Group Records
######################################

Besides user/group records acquired via the aforementioned Varlink IPC interfaces and the synthesized root and nobody accounts, this module also makes user and group accounts available to the system that are defined in static drop-in files in the :code:`/etc/userdb/`, :code:`/run/userdb/`, :code:`/run/host/userdb/` and :code:`/usr/lib/userdb/` directories.

This is a simple mechanism to provide static user and group records via JSON drop-in files. Such user records should be defined in the format described by the `JSON User Records <https://systemd.io/USER_RECORD>`_ specification and be placed in one of the aforementioned directories under a file name composed of the user name suffixed with :code:`.user`, with a world-readable access mode. A symlink named after the user record's UID formatted in decimal and suffixed with :code:`.user` pointing to the primary record file should be created as well, in order to allow both lookups by username and by UID. Privileged user record data (e.g. hashed UNIX passwords) may optionally be provided as well, in a pair of separate companion files with the :code:`.user-privileged` suffix. The data should be stored in a regular file named after the user name, suffixed with :code:`.user-privileged`, and a symlink pointing to it, named after the used numeric UID formatted in decimal with the same suffix. These companion files should not be readable to anyone but root. Example:

.. code-block:: sh

   -rw-r--r--. 1 root root  723 May 10 foobar.user
   -rw-------. 1 root root  123 May 10 foobar.user-privileged
   lrwxrwxrwx. 1 root root   19 May 10 4711.user -> foobar.user
   lrwxrwxrwx. 1 root root   19 May 10 4711.user-privileged -> foobar.user-privileged

Similarly, group records following the format described in `JSON Group Record <https://systemd.io/GROUP_RECORD>`_ may be defined, using the file suffixes :code:`.group` and :code:`.group-privileged`.

The primary user/group record files (i.e. those with the :code:`.user` and :code:`.group` suffixes) should not contain the "privileged" section as described in the specifications. The privileged user/group record files (i.e. those with the :code:`.user-privileged` and :code:`.group-privileged` suffixes) should contain this section, exclusively.

In addition to the two types of user record files and the two types of group record files there's a fifth type of file that may be placed in the searched directories: files that indicate membership of users in groups. Specifically, for every pair of user/group where the user shall be a member of a group a file named ":emphasis:`username`::emphasis:`groupname`.membership" must be created, i.e. the textual UNIX user name, followed by a colon, followed by the textual UNIX group name, suffixed by ".membership". The contents of these files are currently not read, however it is recommended to create them containing an empty JSON object (i.e. "{}"). The mere existence of these files is enough to affect a user/group membership. If a program provides user and/or group record files in the searched directories, it must always also create such files, both for primary and auxiliary group memberships.

Note that static user/group records generally do not override conflicting records in :code:`/etc/passwd` or :code:`/etc/group` or other account databases. In fact, before dropping in these files a reasonable level of care should be taken to avoid user/group name and UID/GID conflicts.

The :code:`systemd-userdb-load-credentials.service` service automatically runs at boot and installs these files from user records passed in via system credentials. See :man-pages:`userdbctl(1)` and :ref:`systemd.system-credentials(7)` for details.

Configuration in :code:`/etc/nsswitch.conf`
###########################################

Here is an example :code:`/etc/nsswitch.conf` file that enables :code:`nss-systemd` correctly:

.. COMMENT: synchronize with other nss-* man pages and factory/etc/nsswitch.conf

.. code-block:: sh

   passwd:         files systemd
   group:          files [SUCCESS=merge] systemd
   shadow:         files systemd
   gshadow:        files systemd
   hosts:          mymachines resolve [!UNAVAIL=return] files myhostname dns
   networks:       files
   protocols:      db files
   services:       db files
   ethers:         db files
   rpc:            db files
   netgroup:       nis
